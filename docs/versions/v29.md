# v29 系列 · DSH / Qoder / WorkBuddy 插件

> 前置：v23（多用户 API）、v22（网关）｜预估 12 天｜**四个次版本**
>
> 目标：把「她」做成一个**本机服务 + 一组插件**，
> 让 DSH、Qoder、WorkBuddy 里的 agent 能直接调用——**后台常驻，随装随用**。

## 为什么要做插件

| 现在 | 做完之后 |
|---|---|
| 只能在 QQ / 自己的 Web 里找她 | **在你写代码的 IDE 里**就能问「她记得我昨天说什么吗」 |
| 记忆只在聊天里 | agent 能把「项目上下文」写进她的记忆 |
| 每个工具各聊各的 | 三端共享同一份记忆和事实卡 |

**本质**：她不再只是一个聊天机器人，而是**你所有工具共用的记忆/人格层**。

## 架构（复用已有两层）

```
DSH 插件      Qoder 插件      WorkBuddy 插件
   │             │                │
   └─────────────┼────────────────┘
                 ↓  127.0.0.1:7070（内部 API，v23）
        ┌────────────────────────────────┐
        │  bot 后端 (v23)                │  聊天 / 记忆 / 事实卡 / 定时
        └────────────────────────────────┘
                 ↑
        （可选）同时监听 0.0.0.0:7080 的网关 → 给公网的手机/网页用
```

**插件直连内部 API，不走网关**：同一台机器，绕一层只会更慢。
网关留给公网（v22 的定位）。

**插件本身很薄**：只负责「把工具调用翻译成一次 HTTP 请求」。

> **多用户**：每个插件实例绑定一个 `user_id`（本机可默认 owner，公网必须走 v23 登录）；
> 工具调用必须带该 `user_id`，`chat/remember/recall/fact` 都只读写这个用户的数据，不能跨用户检索。

## 插件要做的事（三端一致）

| 能力 | 说明 |
|---|---|
| `nao.chat(text)` | 跟她说一句，拿回复 |
| `nao.remember(text)` | 把当前上下文写进她的记忆 |
| `nao.recall(query)` | 检索她记得的事 |
| `nao.fact(slot)` | 取事实卡（比如「我在做什么项目」） |
| `nao.notify(text)` | 让她在 QQ 里提醒你（离开电脑也能收到） |

### 两种接入模式（插件可配置）

插件默认走本机，但**允许改成走公网网关**——比如插件装在笔记本上，她在家里那台机器上。

```jsonc
// ~/.nao/plugin.json
{
  "mode": "local",                          // local | gateway
  "local":   { "url": "http://127.0.0.1:7070" },
  "gateway": {
    "url": "https://nao.example.com",       // 公网网关（v22）
    "token": "<JWT，登录后拿到的>"
  }
}
```

| 模式 | 何时用 | 请求路径 | 鉴权 |
|---|---|---|---|
| **local**（默认） | 插件和机器人同一台机器 | 直连 `127.0.0.1:7070` | 无（仅本机可达） |
| **gateway** | 插件在另一台机器 / 想从外网用 | HTTPS → 网关 → 内部 API | **JWT**（Authorization: Bearer） |

**切换方式**

```bash
nao config mode gateway --url https://nao.example.com
nao config login          # 输入密码换 JWT，存到 ~/.nao/token
nao status                # 显示当前走哪条路 + 连通性
```

**三条规则**

| 规则 | 原因 |
|---|---|
| **默认 local** | 同机时绕公网是自找麻烦 |
| gateway 模式**必须**有 token | 网关不认匿名 |
| 两种模式**同一套工具签名** | agent 侧不需要知道走哪条路 |

**降级**：gateway 模式下网关不通 → 提示「切回 local 或检查网络」，
**不静默重试、不拖住 IDE**。

## v29.0 · 本机服务化（3 天）

| 单元 | 内容 | 验收 |
|---|---|---|
| U1 | `nao-service`：网关 + 后端的统一启动器（守护、重启、日志） | 一条命令起 |
| U2 | **开机自启**：Linux 用 systemd user unit，macOS 用 launchd，Windows 用计划任务 | 重启机器后自动可用 |
| U3 | 健康检查 `/api/health` + `nao status` | 能看「在不在」 |
| U4 | 端口冲突/重复启动的明确报错 | 不会静默失败 |

**关键**：服务化不是把 `run.py` 塞进 systemd 就完事——
还要保证**它和 QQ 那条链路不冲突**（同一个进程只跑一份）。

## 红线

| 红线 | 原因 |
|---|---|
| **只连 127.0.0.1:7070** | 插件是本机工具，不碰公网 |
| token 与 QQ 侧**分开**（网关 token） | 泄露一个不牵连另一个 |
| 插件**不缓存聊天原文**到 IDE 工程里 | 隐私 |
| 服务挂了**不能拖垮 IDE** | 降级为「她暂时不在」 |
| 卸载必须能停服务 | 否则后台偷跑 |

## 风险

| 风险 | 处理 |
|---|---|
| 三端插件机制差异大（MCP / 扩展 / 脚本） | v25.2 先做最像的那个，其余照抄 |
| Windows 自启麻烦 | 先用「启动器 + 快捷方式」过渡 |
| 沙箱/权限限制 | 插件只发 HTTP，不碰文件系统 |
| 版本碎片（三端各一套协议） | v25.2 U1 抽公共核心，禁止各写一套 |

## 验收（系列整体）

| 项 | 标准 |
|---|---|
| 装完即用 | 三端任一装好后能 `nao_chat` |
| 记忆一致 | DSH 里让她记的事，QQ 里问她记得 |
| 后台常驻 | 重启机器后不用手动起 |
| 卸载干净 | 无残留进程/配置 |
