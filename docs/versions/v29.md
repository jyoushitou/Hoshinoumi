# v29 系列 · 存储层插件接口

> 前置：v23 多用户 API / v27 工具层｜预估 3 天｜**三个次版本**
> 目标：把「SQL 怎么写、用 MySQL 还是 SQLite、事务怎么开」收进 **StorageBackend + Repository** 插件层。
> 业务只调仓储方法，不再到处拼 SQL；换存储/加缓存只加适配器。

## 现在的问题

| 现状 | 问题 |
|---|---|
| `infra/repo_*` 直接写 SQL | 换库/加索引要改业务 |
| MySQL / SQLite 方言散落 | `%s` / `?`、`ON DUPLICATE`、视图各写一套 |
| 事务边界不清 | 双写失败难回滚 |
| 多用户 `user_id` 刚加 | 容易漏过滤 |

## 契约

```python
class StorageBackend(Protocol):
    dialect: str                       # mysql / sqlite / memory
    def cursor(self): ...
    def transaction(self): ...

class Repository(Protocol):
    # 每个领域一个仓储：memory / facts / cron / reading / user
    ...
```

- `StorageBackend`：连接/游标/事务/方言；不暴露业务 SQL。
- `Repository`：按领域定义方法（`add` / `search` / `list` / `delete`），**必带 `user_id`**。
- `StorageRegistry`：按配置选 backend；仓储由 backend 装配。

## 关键设计

- **不引 ORM**：手写仓储，SQL 集中在 `infra/repo_*`，保持可控。
- **方言**：backend 负责 `%s`/`?`、DDL、视图；仓储不判断数据库类型。
- **事务**：仓储方法要么自带事务，要么由调用方传 `tx`；双写用同一事务。
- **多用户**：仓储方法签名强制 `user_id`；没传直接报错。
- **迁移**：`scripts/migrate_*` 只依赖 backend 的 DDL 接口；幂等。
- **可观测**：`!db` 显示 backend、慢查询、连接池、迁移版本。

## 验收

```bash
!db                  # backend / 池 / 慢查询 / 迁移版本
```

- 切到内存 backend：测试不用 MySQL/SQLite。
- MySQL 与 SQLite 跑同一套仓储测试，结果一致。
- 业务层（ai/chat/life）里搜不到 `SELECT`/`INSERT`。

## 不做

- 不引 SQLAlchemy/ORM；不把 SQL 藏进魔法。
- 不引入 Redis/外部缓存（v46 前不做）。
- 不让仓储返回裸 cursor 给业务。

## 风险

| 风险 | 处理 |
|---|---|
| 方言差异（`ON DUPLICATE`/视图） | backend 内适配；两库同测 |
| 事务嵌套 | 只允许一层；嵌套直接报错 |
| 迁移中断 | 幂等 + 版本表；失败可重跑 |
| 性能回退 | 保留原 SQL 对照；EXPLAIN 检查 |
