# v26 系列 · 内部通讯升级（8+4+body TCP + protobuf）

> 前置：v24 读书修复 / 本地阅读队列｜预估 11 天｜**八个次版本**
>
> 目标：**外部 → 网关仍走 HTTP/JSON**；**网关 → 后端走本机 TCP + protobuf**。
> v26.7 起由 **ingress** 持有 `3001` / `27004`（支持蓝绿热更新）：
> - `3001`：NapCat WebSocket → worker `qq.sock`
> - `27004`：8+4+body 自定义帧 L4 → worker `internal.sock`
> - worker 只绑 Unix socket，不直接占这两个端口
> 外部 `/api/*` 仍由网关 `27005` 提供 HTTP/JSON。
>
> 原 v25（内部通讯）已顺延为 v26；原 v26（插件接口）顺延为 v27，v27 及以后整体 +1。

## 为什么做

- 内部路径不需要人类可读 JSON
- protobuf 有字段号，加字段兼容
- TCP 长连接省掉每次 HTTP 建连/解析开销
- 帧边界明确，便于做超时/重连/限长
- 与 v23 proto 契约对齐


## 通讯边界（明确）

```text
外部客户端 / Web / App / DSH
        │
        │ HTTP/JSON + JWT
        ▼
   gateway 27005
        │
        │ 8+4+body TCP 帧 + protobuf
        ▼
   backend 27004
        ▲
        │ WebSocket（NapCat 协议）
   NapCat 3001
```

| 链路 | 协议 | 序列化 | 端口 |
|---|---|---|---|
| 外部 → 网关 | HTTP/1.1 | JSON | 27005 |
| 网关 → 后端 | 自定义 TCP 帧 | protobuf | 27004 |
| NapCat → 后端 | WebSocket | NapCat 消息 | 3001 |

规则：

- **后端不监听 HTTP**，27004 只接受 8+4+body 帧。
- **网关对外仍是 HTTP/JSON**，`/api/*` 契约不变。
- 网关负责鉴权、限流、审计，再把请求编码成 protobuf 帧。
- 后端只信任 127.0.0.1 上的网关帧；不做公网认证。
- 外部客户端不能直接连 27004。

### 一次 /api/chat 的路径

```text
客户端 POST :27005/api/chat  JSON
  -> 网关 JWT/限流/审计
  -> InternalRequest{request_id, method="/internal/chat", user_id, payload=ChatRequest}
  -> 8+4+body 帧 -> 后端 27004
  -> 后端 protobuf 解码 -> 业务
  -> InternalResponse{request_id, status, payload=ChatReply}
  -> 帧回传网关
  -> 网关转 HTTP JSON 响应
```

## 帧格式：8 + 4 + body

```text
偏移  长度  字段
0     4     magic = "NAO1"
4     1     version = 1
5     1     type: 1=request 2=response 3=event 4=ping
6     1     flags（保留，默认 0）
7     1     reserved（保留，默认 0）
8     4     body 长度，uint32 大端
12    N     protobuf body
```

规则：

- `8 + 4 = 12` 字节固定前缀，后面才是 protobuf。
- body 最大 8 MiB；超限直接断开并记录。
- 读帧必须处理**半包/粘包**：先读 12 字节，再按长度读 body。
- 长度不合法（0 或 >8MiB）→ 关闭连接。
- 连接是长连接；请求/响应靠 protobuf 里的 `request_id` 关联。
- TCP 只监听 `127.0.0.1:27004`，不暴露公网。
- 后端不绑定 27005；网关是独立进程/容器。

## Protobuf 封装

```proto
message InternalRequest {
  string request_id = 1;
  string method = 2;      // /internal/chat 等
  string user_id = 3;
  string role = 4;
  bytes payload = 5;      // ChatRequest / HistoryRequest ...
}

message InternalResponse {
  string request_id = 1;
  int32 status = 2;       // 200/400/401/403/404/429/503
  string error = 3;
  bytes payload = 4;
}
```

业务 payload 复用 `proto/nao/v1/nao.proto`，逐步补：

```text
ChatRequest / ChatReply
HistoryRequest / HistoryReply
StateRequest / StateReply
CronRequest / CronReply
DiaryRequest / DiaryReply
ShelfRequest / ShelfReply
AuditRequest / AuditReply
AuthVerifyRequest / AuthVerifyReply
```

## v26.6 · 模糊指令 / 钩子创建一致性

> 触发：用户说「提醒我过30min吃药」后，又输入 `! corn` / `!cron`。
> 实际根因不是标准命令：`extract.py` 只认「30分钟后 / 半小时后」，
> 不认「30min」，所以钩子根本没建成；模型却回了「行，我记着了」。

### 目标

```text
自然语言 -> 结构化意图 -> 标准命令草稿
错别字命令 -> 最近的标准命令建议
只提示/确认，不静默执行高风险命令
```

### 单元

| 单元 | 内容 | 验收 |
|---|---|---|
| U0 | 时间解析支持 `30min` / `30 minutes` / `半小时` | `提醒我过30min吃药` 真的建成 once 任务 |
| U1 | 创建失败不能装懂：`extract` 返回空时明确说“没建成” | 不再回“行，我记着了” |
| U2 | 成功创建后回复标准命令草稿 | `!cron add ... once 吃药` |
| U3 | 未知命令做编辑距离/前缀匹配 | `! corn` -> 提示 `!cron` |
| U4 | AI 返回结构化字段：command / args / confidence / missing | 不把自然语言直接拼 shell/SQL |
| U5 | 低置信度只问确认，不执行 | 模糊时回复“你是想…吗？” |
| U6 | 不泄露内部命令参数/密钥 | 提示只含必要参数 |

### 示例

```text
用户：提醒我过30min吃药

奈绪：好，19:10 提醒你吃药。
标准命令：!cron add 19:10 once 吃药
```

```text
用户：! corn

奈绪：你是不是想用 !cron？
用法：!cron list / !cron add ...
```

- 不自动执行未确认的高风险命令
- 不伪造标准命令参数

## 鉴权职责（明确）

```text
backend 27004：只提供 TCP 帧服务，不做公网鉴权
gateway 27005：绑定 HTTP，负责外部鉴权/限流/审计
```

| 事项 | 谁做 |
|---|---|
| 绑定 27004 TCP | backend |
| 绑定 27005 HTTP | gateway |
| 外部 HTTP 请求解析 | gateway |
| JWT 签发/校验 | gateway |
| owner secret 登录 | gateway |
| user_id/password/setup_code 校验 | gateway 调后端 auth 帧，拿结果后签 JWT |
| 限流 60/min | gateway |
| 审计 gateway_log | gateway |
| 帧解码/业务 | backend |
| 信任 user_id/role | backend 只信 127.0.0.1 网关帧 |

后端不保存/校验 access token；JWT 只在网关。
后端仍保存 users/password_hash，因为账号数据在数据库；校验动作由网关发起 auth 帧。


## 迁移与回滚

- 27004 不能同时是 HTTP 和 TCP；v26 是**切换发布**，不是并存发布。
- 发布窗口：停 bot → 启 v26 后端（27004 TCP）→ 启 v26 网关 → 验收。
- 回滚：停 v26 → 启旧后端二进制（27004 HTTP）→ 启旧网关。
- 网关保留 `backend.protocol = "http" | "tcp"` 仅用于滚动回滚；最终默认 `tcp`。
- v26.4 删除网关内部的 HTTP 客户端路径与后端 aiohttp API。

## 验收

```text
1. 12 字节前缀正确，body 是 protobuf
2. 半包/粘包/超长/错 magic 都有测试
3. gateway -> 27004 完成 chat/history/state（代码路径已切；生产验收按 DEPLOY-v26.md）
4. 后端只监听 3001/27004，无 HTTP 监听
```
