# v27 系列 · 通道层插件接口

> 前置：v23 多用户 API / v24 模型层｜预估 3 天｜**三个次版本**
> 目标：把「QQ 怎么收、怎么发」从 `chat/`、`egress/` 里抽出来，
> 变成可注册的 **Channel 接口/扩展点**：QQ（NapCat）、Web、以后微信都走同一套接口。
> **NapCat 仍是 QQ 通道适配器，不是 v20 体系网关。**
>
> **核心不插件化**：QQ/NapCat 是 native Channel，不注册为插件、不走 manifest；
> 插件只新增 Web/微信/外部通道；卸载/禁用/失败时自动回退 QQ。

## 现在的问题

| 现状 | 问题 |
|---|---|
| 发送写死 `send_private_msg` / `send_group_msg` | 加 Web/微信就要到处 if |
| 入站写死在 `chat/inbound.py` | 新通道要复制解析 |
| QQ 限流/重连散落在 send/outbound | 不能按通道统一 |
| 主动推送（v28）需要多入口 | 没有统一 Channel 无法扇出 |

## 契约

```python
class Channel(Protocol):
    name: str                          # qq / web / wechat
    def capabilities(self) -> set[str]: ...  # text/image/voice/at/quote/recall
    async def send(self, endpoint: Endpoint, msg: Message) -> str: ...
    async def health(self) -> ChannelHealth: ...
```

- `Endpoint`：`user_id` / `endpoint_id` / `channel` / `device_id`
- `Message`：`text` / `images` / `at` / `voice` / `quote`
- `ChannelRegistry`：按 `channel:` 前缀取用；`send()` 统一入口

## 关键设计

- **QQ 适配器**包现有 `send.py`/`inbound.py`，不改 OneBot 协议；NapCat 仍是 QQ 通道。
- **Web 适配器**：客户端连上时注册 `endpoint`；发送走 WS；断线注销。
- **目标前缀**：`qq:<id>` / `web:<endpoint_id>`；旧 target 默认 qq，兼容现有数据。
- **限流**：每通道/每 endpoint 令牌桶 + 有界队列；平台层（QQ 频率）和用户层分开。
- **能力**：`capabilities()` 决定能不能发图/语音/引用；不支持就降级文本。
- **不跨层**：Channel 只收发，不拼 prompt、不查记忆、不调模型。

## 验收

```bash
!channels            # 列出 qq/web 在线、能力、队列、最近失败
```

- QQ 收发与 v23 基线一致，回归全绿。
- Web 通道能注册、收主动消息、发文本/图片。
- 关掉 Web 不影响 QQ；QQ 断线不影响 Web。

## 不做

- 不实现微信（v41 再做；本版只留接口）。
- 不让 Channel 直接连数据库/模型。
- 不把 NapCat 塞进 v20 网关。

## 风险

| 风险 | 处理 |
|---|---|
| QQ 适配器改变现有行为 | 先包一层，保持旧路径开关；基线测试 |
| Web 连接风暴 | endpoint 去重 + 退避 + 心跳超时 |
| 能力不一致 | 不支持就降级，不报错给用户 |
| 限流误伤 | 平台层/用户层分开，可配 |
