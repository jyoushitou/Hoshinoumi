# v47 系列 · 视频通话

> 前置：v37（语音通话）｜**没有语音通话就别做视频**

> 文字 → 语音 → 图像。最后一步是「看得见」。

## 前提

依赖 v37（语音通话）的音频通道。**没有语音通话就别做视频**。

## 现成的轮子（GitHub 上找过，结论不太乐观）

| 项目 | 情况 | 能不能用 |
|---|---|---|
| [koishi-plugin-rtc-bridge](https://www.npmjs.com/package/koishi-plugin-rtc-bridge) | 实时语音桥，作者只做了音频 | 参考架构，**不含视频** |
| [Lagrange.Core #600](https://github.com/LagrangeDev/Lagrange.Core/issues/600) | **连发个视频文件都发不出去** | 说明视频能力还很弱 |
| [qq-voice-call-bridge](https://github.com/mmmmm406/qq-voice-call-bridge) | v25 的语音桥 | 看它有没有视频分支 |
| [webrtc_server_node](https://github.com/ddssingsong/webrtc_server_node) | 通用 WebRTC 信令服务 | 和 QQ 无关，但能借鉴 |

**结论**：**实时视频目前没有可靠的现成方案**。
所以计划要反过来写——**退路当主路，真视频当加分项**。

## 三档目标（从易到难）

| 档位 | 内容 | 可行性 |
|---|---|---|
| **L1 视频消息** | 发一段 3-10 秒的短视频/动图 | ✅ 能做（复用它现有的发图能力） |
| **L2 带图的电话** | 语音走通话，画面按 2 秒一张轮播 | 🟡 看 v25 通了没有 |
| **L3 真实时视频** | 双向音视频流 | ❌ 暂无轮子，靠逆向协议 |

**v29 先做 L1**（一定能交付），L2 视 v25 结果，L3 只在找到可用协议时才碰。

## 可能的路径

| 方案 | 做法 | 风险 |
|---|---|---|
| A. QQ 视频通话信令 | 同 v25，逆向协议 | 更高（视频权限、带宽、封号） |
| B. 视频消息（退路） | 发一段短视频/动图，不是实时 | 成本低，但不算「通话」 |
| C. 画面 + 语音分离 | 语音走通话，画面走静态图轮播 | 折中，像「带图的电话」 |

## 真做的技术点

| 点 | 说明 |
|---|---|
| 视频编码 | H.264 / VP8，实时编码吃 CPU |
| 带宽 | 至少 500kbps 上行，家宽要够 |
| 形象 | 用 Live2D/3D 还是静态图？算力差别巨大 |
| 隐私 | 你的摄像头画面要不要给她看？默认**不看** |

## 红线

- **不主动发起视频**
- **不开启摄像头采集**（除非你明确说）
- 视频流不落盘、不转发

## 验收

| 档位 | 标准 |
|---|---|
| L1 视频消息 | 能生成一段短视频/动图并发出，对方能播放 |
| L2 带图的电话 | 通话中画面 2 秒一换，不卡 |
| L3 真实时 | 画面 5 秒内出现，音画偏差 < 200ms |

**最低交付**：L1。做到 L2 算超预期，L3 不承诺。

## 与 v37 / v40 的关系

```
v37 语音通话 → v38 视频通话（依赖音频通道） → v40 常驻（跑得稳）
```
