# v35 系列 · 多端与客户端

> 大版本 v35。当前已实现 v35.1.0.0、v35.2.0.0、v35.2.1.0；下一步 **v35.2.2.0 DSH 插件骨架**，按次次版本推进。
> 技术栈：
> Vue Web + Vue 套壳（快速多端）+ Qt 桌面（深度优化）+ 原生手机（深度优化）。
> 先做聊天室基础，再做全量可视化/平台增量；每个次版本是验收节点。

## 1. 客户端形态

```text
Web          Vue 3 + Vite，浏览器直接访问
Vue 套壳      TypeScript + Tauri/WebView，只做兼容兜底
Qt 桌面      Qt 6 + QML/C++，原生深度客户端 + 后台小窗
Android 基线 Kotlin + Jetpack Compose，通用安卓
小米 Rust    Rust + JNI/NDK，澎湃 OS 4（HyperOS 4）专项
iOS          先评估，不阻塞 v35
```

共享：

```text
REST / SSE 协议
DeliveryHub endpoint
本机服务
同一套账号/历史/消息
```

不共享：

```text
Qt/原生不强行复用 Vue DOM
套壳只做兼容兜底，不替代深度客户端
深度客户端按平台/厂商单独开发
```

## 4. 存钱记录（schema 34）

```sql
savings_goals (
  id, user_id, name, target_cents, saved_cents,
  deadline, status, created_at, updated_at
)

ledger_entries (
  id, user_id, kind, amount_cents, category,
  note, occurred_at, goal_id, created_at
)

ledger_categories (
  id, user_id, name, kind, created_at
)

finance_accounts (
  id, user_id, account_type, name, balance_cents,
  currency, updated_at
)

finance_balance_snapshots (
  id, account_id, balance_cents, note, recorded_at
)

api_balance_snapshots (
  id, provider, currency, total, granted,
  topped_up, available, fetched_at
)

calorie_entries (
  id, user_id, food, calories, protein_g, carbs_g, fat_g,
  meal, occurred_at, source, confidence, estimate_json,
  image_ref, created_at
)

calorie_goals (
  user_id, daily_target, updated_at
)
```

账户类型：

```text
bank      银行卡
alipay    支付宝
wechat    微信
cash      现金
other     其他
```

录入方式：

```text
手动输入余额
可选记一笔支出/收入
不做银行/支付宝/微信 API 接入
不自动扣款
```

对账：

```text
新余额 vs 上次余额 - 期间流水
差额显示“待对账”
允许手动调整，不偷偷改
```

- `ledger_entries.account_id` 可选，关联账户
- `ledger_entries.source`：manual / chat
- `raw_hash`：聊天自动记账去重
- `kind`: income / expense / saving
- 金额用整数分，不用浮点
- 月度流水 = 当月 income/expense/saving 汇总
- 存钱目标进度 = saved_cents / target_cents
- 只记录，不接银行、不做理财建议
- 仅 owner
- 可设每月/每周存钱提醒（只提醒，不自动扣款）

### 后端进程名：run → nao-run（v35.2.26.0）

目标：进程列表、systemd 日志、supervisor、文档里不再出现裸 `run` 作为后端进程名。

```text
进程标题      nao-run
Linux comm    nao-run（PR_SET_NAME / setproctitle）
systemd       nao-run.service；SyslogIdentifier=nao-run
supervisor    worker-cmd = python3 -u nao-run
兼容入口      run.py 保留，行为不变
Windows       任务管理器显示 nao-run（包装器/启动器）
```

验收：

```text
pgrep -x nao-run 能命中
ps -o comm= -p <pid> 输出 nao-run
journalctl -t nao-run 能看到后端日志
python3 run.py 仍能启动
supervisor 切换/重启不退化
```

### 聊天已读与已读不回

在线状态：

```text
后端连接 = 在线
无连接 = 离线
前台/后台分开显示
多端取“任一在线”
QQ 在线状态不参与判断
```

已读：

```text
仅自研客户端显式上报 last_read_message_id
服务端写 message_reads
广播给同一用户其他 endpoint
多端已读一致

QQ 无法拿到可靠已读回执
→ 不显示已读
→ 不推断已读
→ 不触发已读不回
```

已读不回：

```text
仅主人私聊
仅自研客户端的显式已读事件
QQ / 无回执渠道 → 永不触发
阈值默认 30 分钟
先判断话题是否结束
  closed     → 不追问、不降亲密
  open       → 可主动追问一次
  uncertain  → 不追问
免打扰/静音/前台正在输入 → 不触发
群聊/他人 → 永不触发
```

动作：

```text
默认：主动发一次对话
可选：closeness 小幅下降
不叠加惩罚，不刷屏
```

话题判断：

```text
输入：最近 N 轮对话
输出：closed / open / uncertain + confidence + reason
仅 open 且 confidence ≥ 0.7 才追问
模型失败/超时 → uncertain → 不追问
```

追问：

```text
一次/话题
全局最多 2 次/天
冷却 6 小时
用户回复/发新消息 → 取消
不质问“为什么不回”
不制造愧疚
```

强制结束：

```text
!topic close   当前话题手动 closed
!topic open    重新打开
!topic status  查看状态

manual_closed 优先级最高
模型再返回 open 也不追问、不扣分
直到主人发下一条新消息
或 !topic open
```

事件：

```text
interaction_events.type = topic_followup
interaction_events.type = topic_ignored
```

衰减：

```text
首次追问无回应 → 不扣
24h 内第 2 个 open 话题仍被忽略
→ 才发 topic_ignored
→ 由 v37 扣多维，不直接改 affinity
```

多维扣分：

```text
closeness     -0.010
security      -0.005
tension       +0.010
support       -0.005
reciprocity   -0.005
```

上限：

```text
最多 1 次/天
closeness 最多 -0.03/周
closed/uncertain 不扣
QQ 无已读不扣
回复/修复后停止累计
```

### 热量识图

```text
拍照/上传食物图
→ vision 识别食物与份量
→ 输出 calories/protein/carbs/fat + confidence
→ 用户确认
→ 写 calorie_entries
```

规则：

```text
source = vision
confidence 低 → 追问份量/文字，不硬记
只给估算，不提供医疗建议
```

```text
识别不出 → 提示手动输入
模型超时 → 不写 0
单位/份量不明 → 先问再算
```

### 内存预算

### 进程拆分

```text
:ui     前台才起，动画/图片/列表
:push   后台常驻，只做心跳/收消息/通知
```

:push 约束：

```text
不加载 UI
不加载图片
不打开大 DB
只保留连接/队列/通知
目标 PSS ≤ 30MB
```

前台策略：

```text
切前台 = 性能全给
动画可开
允许到 1GB
切后台 = 降档/清缓存
```

### 桌面内存预算

桌面和手机不同，不要求只开一个窗口：

```text
Qt 原生桌面：
  前台 UI        ≤ 4GB（硬上限）
  后台 daemon    ≤ 50MB（托盘/连接/通知）

Vue/Tauri 兼容套壳：
  前台           ≤ 4GB
  后台           ≤ 80MB（兼容放宽）
```

进程拆分：

```text
desktop-ui      主窗口/聊天/小窗
desktop-daemon  托盘/WebSocket/通知
```

规则：

```text
关主窗 → UI 可退，daemon 保活
daemon 不加载聊天历史/图片
开主窗 → UI 重新拉数据
```

### 体积预算

```text
原生 Android APK（arm64）   ≤ 30MB
Vue 套壳 APK                 ≤ 50MB
Qt 桌面安装包                ≤ 100MB
```

“兼容可以放宽”不等于可以到几百 MB。

### 按机型分档

以 **PSS** 为准，Release 包、亮屏空闲 5 分钟后测：

```text
澎湃 OS 4 / 8GB：
  后台/空闲          ≤ 100MB
  前台动画关闭       约 100MB
  前台动画开启       允许到 1GB，硬上限

EMUI / 6GB：
  后台/空闲          ≤ 100MB
  前台动画关闭       约 100MB
  前台动画开启       尽量 ≤ 512MB，硬上限 1GB
```

切后台 / 锁屏：

```text
暂停动画
清图片缓存
回到 100MB 档
```

动画开关：

```text
默认关闭
开启后更丝滑
低电量/后台/6GB 机型自动降级
```

分解：

```text
Kotlin/Java heap   ≤ 48MB
Rust/native        ≤ 30MB
图形/图片缓存      ≤ 32MB
其他               余量
```

手段：

```text
不用 WebView
Kotlin Views，不用 Compose 起步
图片 LRU + 解码尺寸限制
列表虚拟化/懒加载
不做常驻大对象
Release + R8
```

测量：

```bash
adb shell dumpsys meminfo <包名>
```

100MB 是“动画关闭/后台”目标；开启动画后允许到 1GB，但切后台必须降回 100MB 档。


```text

ntfy/WebSocket 只能提高存活率
```

### 澎湃 OS 4 约束

```text
目标系统：HyperOS 4（澎湃 OS 4）
架构：arm64-v8a
不以 GMS 为前提
厂商推送/后台限制以 HyperOS 4 实机为准
Rust + JNI/NDK；Android UI 薄层
真机验收：HyperOS 4 小米设备
```

桌面端同理：

```text
Qt 是桌面深度主线
Linux / Windows 分别打包、分别验收
特殊 OEM/硬件再单开 Rust 变体，不混入主线
```

## 10. 风险

- 四套 UI 成本高：Vue/套壳先验证，Qt/原生按验收节点推进。
- 协议不一致：所有客户端共用同一 REST/SSE 契约测试。
- 套壳与深度客户端功能漂移：明确套壳只做基础。
- Qt/原生打包：Linux/Windows/Android 分开验收。
- iOS 不确定：只做评估，不阻塞 v35。
