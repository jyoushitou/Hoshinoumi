# v18 系列 · 情感的深刻度

> 前置：v17（执行模型 + 情绪/声线）｜预估 11 天｜**六个次版本**
>
> **核心命题**：人不是「24 小时清零」的机器。
> 今天被骂一句，明天还记着；被温柔对待一次，能记好几年。
> 记忆和情绪都该有**分量**：轻的很快淡，重的留得久。

## 现在的问题

```
mood 每小时往基线回归  →  睡一觉，昨天的气没了
记忆全按 importance=2  →  「你妈住院」和「今天吃了面」一样重
情绪只影响当次回复      →  昨晚吵架，今天她像没事人
```

**结果**：她的记忆是「平的」，所有事一样重，所有情绪一样短。

## 目标：三档分量

| 档 | 例子 | 记忆留存 | 情绪衰减 |
|---|---|---|---|
| **轻** | 今天吃了什么、随口吐槽 | 7 天 | 半衰期 1 天 |
| **中** | 工作不顺、和朋友闹别扭 | 90 天 | 半衰期 3 天 |
| **重** | 亲人离世、重病、重要约定、表白/分手 | **长期（不清）** | 半衰期 5 天 |

**「重」的记忆不按天删**——它进「长期记忆」区，检索时永远高优先级。

## 索引与视图规范（v18.0 U7）

> 一条硬规矩：**给视图写查询之前，先确认基表有索引**。
> 视图本身不能建索引（MySQL/SQLite 都不支持物化视图），
> 它只负责翻译方言和派生字段，**性能全靠底下的表**。

### 先纠正一个常见误解

| 想法 | 事实 |
|---|---|
| 「给视图加索引」 | ❌ 视图是查询的别名，没有自己的存储，加不了索引 |
| 「建了视图就快了」 | ❌ 视图不改变执行计划，慢还是慢 |
| 「索引加在视图上」 | ❌ 只能在**基表**的列上建 |

**正确做法**：视图 → 基表 → 基表上的索引。三层各司其职。

### 索引清单（v18.0 要建的）

| 表 | 索引 | 为什么 |
|---|---|---|
| `memories` | `idx_mem_target_weight (target_id, weight DESC)` | 检索按对象 + 分量排序（v18.0 U3 要用） |
| `memories` | `idx_mem_kind_time (kind, created_at)` | 按类型看时间线 |
| `memories` | `idx_mem_dedupe (target_id, dedupe_key)` UNIQUE | 幂等写入 |
| `bot_meta` | 主键 `key_name` | 键值查询（自带） |
| `cron_tasks` | `idx_enabled_next (enabled, next_ts)` | 已有 ✅ |
| `cron_tasks` | `idx_target (target_id)` | 已有 ✅ |
| `relations` | 主键 `target_id` | 一人一行（自带） |
| `habits` | `idx_habit_target (target_id)` | 按人取口头禅 |
| `reading_progress` | 主键 `target_id` | 一人一行 |
| `qzone_log`（v19 新增） | `idx_qzone_time (posted_at)` | 按时间倒序看发了什么 |

### 命名与数量纪律

| 规则 | 说明 |
|---|---|
| 命名 | `idx_<表缩写>_<列>`，如 `idx_mem_target_weight` |
| 每表上限 | **≤ 5 个**（写多读少的表要克制，索引也是要维护的） |
| 复合索引 | 把**区分度高**的列放前面（`target_id` 通常比 `kind` 区分度高） |
| 时间列 | 凡是 `ORDER BY xxx_time DESC` 的都建索引 |
| 唯一约束 | 用 `UNIQUE INDEX`，不要只靠应用层判重 |

### 迁移脚本

`scripts/migrate_indexes.py`（新）：

```bash

```

**幂等**：用 `CREATE INDEX IF NOT EXISTS`（MySQL 8 不支持这个语法，

## v18.1 · 视觉修复（1 天）

> 修 L7：她把图「发」给了模型，但 `deepseek-flash` 不收图，
> 所以永远退回「看不清」文案。**这是核心功能失效，排在最前面。**

### 本来就是两段式，只是第一段配错了

```
用户发图
   ↓ 压缩成 base64
【第一段】视觉模型（豆包）看图 → 一句描述 + 3~5 个标签
   ↓ 纯文本（描述 + 标签）
【第二段】对话模型（DeepSeek）拿着描述接话
   ↓
她回「这猫在窗台上晒太阳呢」
```

**代码结构早就是这样**（`ai/vision.py` 只负责「图 → 文字」，
`ai/client.py` 再把文字拼进 prompt）。**缺的只是第一段指向谁**：

| 段 | 现在指向 | 应该指向 |
|---|---|---|
| 看图 | `api.deepseek.com` + `deepseek-flash` ❌ 不收图 | 豆包视觉（`ark.cn-beijing.volces.com` + `doubao-vision-pro`） |
| 对话 | DeepSeek ✅ | DeepSeek（不变） |

**所以这不是「换架构」，是「换一个 URL 和一个 key」。**

| 单元 | 内容 | 验收 |
|---|---|---|
| U1 | 加 `NAO_VISION_KEY`；key 顺序：专用 → `DOUBAO_API_KEY` → `DS_API_KEY` | 配豆包 key 就能看图 |
| U2 | 默认端点改豆包视觉（`ark.cn-beijing.volces.com`），模型 `doubao-vision-pro` | 开箱能识图 |
| U2b | 降级链：豆包视觉失败 → 尝试 DeepSeek（若支持）→ 都不行退「看不清」 | 不因一段挂掉整条链 |
| U3 | 失败时日志打 **HTTP 状态码 + 响应前 200 字** | 一眼看出 400/401 |
| U4 | 连通性自检：`!vision test` 发一张内置图，报成功/失败原因 | 一条命令验通 |
| U5 | 视觉失败仍退回「看不清」，但日志能定位 | 不静默 |

**改动文件**：`ai/vision.py`、`cmd/ops.py`（加 `!vision test`）、`发布检查清单` 环境变量表。

**红线**：不把图片内容写进日志；key 只从环境变量读。

### 具体改法（v18.1 开工时照这个做）

**① `ai/vision.py` 顶部：key / url / model 三处**

```python
# 之前
DEFAULT_VISION_MODEL = os.getenv("NAO_VISION_MODEL", "deepseek-flash")
DEFAULT_VISION_URL = os.getenv("NAO_VISION_URL",
                               "https://api.deepseek.com/v1/chat/completions")
# 请求头里：Authorization: f"Bearer {cfg.DS_API_KEY}"

# 之后
DEFAULT_VISION_MODEL = os.getenv("NAO_VISION_MODEL", "doubao-vision-pro-32k")
DEFAULT_VISION_URL = os.getenv(
    "NAO_VISION_URL",
    "https://ark.cn-beijing.volces.com/api/v3/chat/completions")

def vision_key():
    """视觉用哪个 key：专用 → 豆包 → DeepSeek（最后一个是兜底）"""
    return (os.getenv("NAO_VISION_KEY")
            or getattr(cfg, "DOUBAO_API_KEY", "")
            or getattr(cfg, "DS_API_KEY", ""))
```

**② 失败日志要能看出是哪一步挂的**

```python
resp = await run_blocking(_post, timeout=40, name="vision")
if resp.status_code != 200:
    log_api(f"[视觉] HTTP {resp.status_code} | {resp.text[:200]}")
    return None, []
```

现在只记 `失败 400`，没有响应体，看不到「不支持 image_url」这句话。

**③ 降级链（U2b）**

```python
async def describe_image(img_bytes):
    for provider in providers():          # [豆包, DeepSeek]
        try:
            out = await _try(provider, img_bytes)
            if out and out[0]:
                return out
        except Exception as e:
            log_api(f"[视觉] {provider.name} 失败：{e}")
    return None, []
```

**④ 配置示例（`config.example.json`）**

```json

    "url": "https://ark.cn-beijing.volces.com/api/v3/chat/completions",
    "model": "doubao-vision-pro-32k",

  }

```

**⑤ 自检命令（U4）**

```

→ 🖼️ 视觉：豆包 ✅（0.8s，描述「一只橘猫在窗台上」）
→ 🖼️ 视觉：豆包 ❌ HTTP 401（key 不对）
```

用一张内置的测试图（`tests/assets/cat.jpg`），不依赖用户发图。

**⑥ 验收步骤**

```bash
#    她能说出「橘猫」「窗台」这类具体内容，而不是「看不清」
```

**⑦ 回滚**

改的都是环境变量 + 三行默认值：

```bash

NAO_VISION_URL=https://api.deepseek.com/v1/chat/completions python3 run.py
```

**⑧ 成本提醒**

两段式 = 两次 API 调用。一张图大约：

| 段 | 消耗 |
|---|---|
| 豆包视觉 | 图片 token（约 1000~2000 tokens/张） |
| DeepSeek 接话 | 正常对话 tokens |

**发图频率低的话完全可接受**；如果一天几十张，考虑加「同一张图只描述一次」的缓存（记在 `images` 表，按 md5 去重）。

**衰减公式**：

```python

power *= factor ** days_elapsed
if power < 0.15:  # 消散
    return "平静"
```

## v18.3 · 回忆触发（2 天）

> 重记忆不是「存着等检索」，而是**会自己冒出来**。

| 单元 | 内容 | 验收 |
|---|---|---|
| U1 | 每天最多一次「突然想起」 | 不刷屏 |
| U2 | 只挑 `weight ≥ 0.7` 且 7 天没提过的 | 不重复念叨 |
| U3 | 提起时带时间：「上周你说你妈住院」 | 有时间感 |
| U4 | 她情绪低落时不提旧伤口 | 有分寸 |

**触发时机**：`idle_tick` 安静时，命中概率 20%，每天上限 1 次。

**红线**：不拿重记忆当谈资；不主动提创伤事件（除非主人先提）。

## 红线（整个系列）

- **重记忆不自动删**：只有主人 `!forget` 才能删
- 情绪**必须有消散路径**（上限 1.0，最低回到平静）
- 分量判定**宁可判轻**：判重了会让她反复提旧事
- 不做「情绪历史库」：只留最近一次情绪 + 强度

## 验收（系列整体）

| 项 | 标准 |
|---|---|
| 重记忆留存 | 30 天后还能检索到亲人/重病类记忆 |
| 轻记忆衰减 | 7 天前的「吃了面」不再被想起 |
| 情绪跨天 | 第 2 天聊天气氛仍受前一天影响 |
| 主动提起 | 一周内至少一次「突然想起」 |

## v18.4 · 进程内 TTL 缓存（2 天）

> 为什么不直接上 Redis：瓶颈在模型调用（秒级），数据库查询是毫秒级；
> 单机单进程没有跨进程共享需求；加 Redis 还会破坏「MySQL 连不上退 SQLite」的退路。
> **进程内缓存就够**，而且可比 Redis 更快（没有网络往返）。

| 单元 | 内容 | 验收 |
|---|---|---|
| U1 | `infra/cache.py`：get/set/invalidate/stats，TTL | 命中返回旧值，过期重新读 |
| U2 | `repo_query.counts()` 走 5 秒缓存（传游标时不缓存） | `!stats` 连点不压库 |
| U3 | `cron.list_tasks()` 走 3 秒缓存，增删改后失效 | `!cron` 改完立刻看到新任务 |
| U4 | `!stats` 显示命中率 | `⚡ 缓存：命中率 99%｜1 键` |
| U5 | 失效策略：写操作后 `invalidate(prefix)` | 不会出现「改了看不见」 |

**三条纪律**

1. **传游标就不缓存**：测试、事务里必须读实时
2. **写后必失效**：`add/remove/set_enabled` 之后清列表缓存
3. **异常不缓存**：生成函数抛错时不写缓存，避免把失败固化

**收益（v18.0 实测过，已回退）**：同一统计 200 次，5.3ms → 0.2ms，约 23 倍。

**不做 Redis 的判断写进文档**，将来若出现「多机部署」或「DB 查询 > 50ms」再评估。

## v18.5 · 收尾：彻底移除旧表

> v17.10 只做了第 1 步（停写）。到这里旧表已经只读不写一段时间了，
> 可以一次清干净——**这一步不可逆**。

| 步 | 做什么 | 检查 |
|---|---|---|
| 1 | 备份整库：`mysqldump ... > backup-before-drop.sql` | 备份文件非空、能 grep 到 `events` |
| 2 | 停读：旧 JSON 读函数改读新表，去掉 `events` 回退 | 日志里不再出现「回退旧表」 |
| 3 | 标旧行：`UPDATE events SET deleted_at=NOW() WHERE kind NOT IN (...)` | 行数对得上 |
| 4 | 改名留档：`RENAME TABLE events TO events_old_YYYYMMDD` | 旧查询全部报错即证明没漏 |
| 5 | 删合并逻辑：`repo_memory` 里新旧字段 merge 分支 | 单测仍绿 |
| 6 | 删 `store_v2` 回退分支 + 删 `NAO_LEGACY_WRITE` 开关 | `grep -r "NAO_LEGACY_WRITE"` 为空 |

**验收**：

- `SHOW TABLES` 里没有 `events`（只有 `events_old_*` 留档）
- `grep -r "FROM events" botv/` 结果为空或只剩注释
- 全量测试绿
- 跑 24 小时无「表不存在」报错

**回退方案**：只有第 4 步（改名）可逆——`RENAME TABLE events_old_* TO events`。
第 5、6 步删掉的代码靠 git 回滚。

**为什么放收尾版**：这类「删数据路径」的改动必须单独一版、单独验证，
和功能开发混在一起，出问题分不清是谁的锅。

### L6 方案：元数据表 + 视图解耦

**第一步：表（存事实）**

```sql
CREATE TABLE bot_meta (
    key_name   VARCHAR(64) PRIMARY KEY,
    value      TEXT NOT NULL,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
-- 首次启动写一次，之后只读
-- INSERT IGNORE INTO bot_meta(key_name, value) VALUES('first_start', NOW());
```

**第二步：视图（给查询层用的稳定接口）**

```sql
CREATE VIEW v_bot_meta AS
SELECT
    key_name,
    value,
    updated_at,
    CASE key_name
        WHEN 'first_start' THEN DATEDIFF(NOW(), value)      -- 天数（MySQL）
        ELSE NULL
    END AS days_since
FROM bot_meta;
```

**第三步：代码只认视图**

```python
# infra/repo_meta.py（新）
def uptime_days(cursor=None):
    c = cursor or get_cursor()
    c.execute("SELECT days_since FROM v_bot_meta WHERE key_name='first_start'")
    ...
```

| 层 | 谁在用 | 能改吗 |
|---|---|---|
| `bot_meta` 表 | 只有 `repo_meta` 写 | 结构可变，视图负责兜住 |
| `v_bot_meta` 视图 | `repo_meta` 读、命令层读 | **对外契约**，改要同步 |
| 命令层 | 只调 `repo_meta.uptime_days()` | 不碰 SQL |

**为什么用视图而不是直接读表**

1. **换存储不用改代码**：以后 `first_start` 从 MySQL 挪到 SQLite/文件，
   只改视图定义，`repo_meta` 和命令层不动
2. **算天数有方言**：MySQL 用 `DATEDIFF`，SQLite 用
   `julianday('now') - julianday(value)`——**视图里吃掉方言**，
   上层拿到的永远是「天数」这个统一语义
3. **可加派生字段**：以后想看「运行几小时」「首次启动是周几」，
   加进视图即可，不动表

**方言适配要补一块**

`infra/schema.py` 现在只管 `CREATE TABLE`，要加 `VIEWS` 字典 +
`adapt_ddl(..., kind="view")`，把 `DATEDIFF(NOW(), x)` 翻成
`CAST(julianday('now') - julianday(x) AS INTEGER)`。
