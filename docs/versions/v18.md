### U8 说明：为什么要「自定义时钟」

现在时区在 `core/clock.py` 里**写死** `CST = UTC+8`。问题是：

| 场景 | 写死的后果 |
|---|---|
| 你在国外/服务器在别的时区 | 得改代码 |
| 想模拟「明天」测试定时 | 改系统时间，影响整台机器 |
| 单元测试要冻结时间 | 只能 monkeypatch，容易漏 |
| 以后多角色（不同时区） | 做不了 |

**目标**：时间来源变成**可配置 + 可注入**，默认仍是东八区。

```jsonc
// config.local.json
{
  "clock": {
    "timezone": "Asia/Shanghai",   // 默认
    "offset_minutes": 0             // 可选：整体偏移（测试/调试用）
  }
}
```

```bash
NAO_TZ=Asia/Tokyo python3 run.py        # 环境变量覆盖
NAO_CLOCK_OFFSET=+60 python3 run.py     # 整体快 60 分钟
```

**代码形态（三条）**

```python
# core/clock.py
def timezone() -> tzinfo: ...     # 读配置/环境变量，默认 CST
def now() -> datetime: ...        # datetime.now(timezone()) + offset
def naive() -> datetime: ...      # 同上但去掉 tzinfo

# ports/clock.py —— 已经是端口，保留
class Clock(Protocol): def now(self) -> datetime: ...

# 使用方（cron / log / txtlog）
from ..core import clock          # 只调函数，不自己算时区
```

**测试怎么冻结时间**

```python
from bot.core import clock

clock.use_fake(datetime(2026, 11, 12, 7, 30))   # 只影响测试进程
...
clock.reset()                                    # 恢复真实时间
```

**红线**

- 默认值不变（`Asia/Shanghai`），**不配置就跟现在一样**
- 偏移只影响「她认为的现在」，**不影响数据库里的时间戳**（`created_at` 仍用库时间）
- 冻结时钟只允许在测试里用，生产环境调用要打警告

### 补充：15 处裸 `now()` 全清单（2026-11-12 扫盘）

v18.0 原计划只点了 6 处（`log.py` 5 + `cron.py` 1），实际扫盘是 **15 处**。
漏掉的 9 处里有 3 处会直接导致功能错 8 小时：

| # | 位置 | 用途 | 错 8 小时的后果 | 原计划 |
|---|---|---|---|---|
| 1–5 | `bot/log.py:111,116,121,126,131` | 控制台/文件时间戳 | 排障时对不上真实时间 | ✅ 已列 |
| 6 | `bot/schedule/cron.py:23` `_now()` | 算下次触发 | **07:30 变 15:30 触发** | ✅ 已列 |
| 7 | `bot/schedule/extract.py:64` | 「今晚八点」的基准 now | **所有口语时间偏 8 小时** | ❌ 漏 |
| 8 | `bot/executors/cron.py:106` | 写 `last_fire` | 与库里其他 CST 时间不一致，interval 任务错乱 | ❌ 漏 |
| 9 | `bot/cmd/query.py:68` | 运行时长 = now − DB `created_at` | DB 存 CST、now 是 UTC → **多算 8 小时** | ❌ 漏 |
| 10–12 | `bot/infra/txtlog.py:68,79,104` | 日志文件名日期 / 行时间 / 保留期 cutoff | 每天 08:00 才换文件；保留期差 8 小时 | ❌ 漏 |
| 13–15 | `bot/diary/cache.py:19,32` | 缓存 TTL 用 `.timestamp()` | 边界时间算错（影响小，但同源） | ❌ 漏 |

**为什么 #7、#8、#9 比日志更重要**：

- `extract.py` 口语解析是**用户直接输入的时间**（「半小时后」「今晚八点」），
  基准错 8 小时 = 提醒全错。
- `executors/cron.py` 把 UTC 写进 `last_fire`，与 `schedule/cron.py` 按 CST 读的
  值混在一起，`interval` 类型的下一次会算错。
- `cmd/query.py` 的 `!uptime` 会把运行时长显示成多 8 小时（DB 已经是 CST）。

### 两种改法的关系（不要二选一）

| 层 | 做法 | 解决 | 局限 |
|---|---|---|---|
| 进程级 | `os.environ["TZ"]="Asia/Shanghai"; time.tzset()` | 所有 `datetime.now()` 一次性变对 | **Windows 没有 `time.tzset()`**，本地开发不生效；且只在启动时生效 |
| 代码级 | 显式 `now(CST)` / 统一时钟模块 | 与进程时区无关，测试可断言 | 要逐处改（15 处），容易漏 |

**建议**：两个都做——进程级兜住「漏改的地方」，代码级保证「关键路径确定正确」。
只做进程级的话，Windows 上跑测试仍然是 UTC，本地与线上一半对一半错。

**代码级的最小实现**（不引入新依赖）：

```python
# bot/core/clock.py
CST = timezone(timedelta(hours=8))

def now():        return datetime.now(CST)                    # 带时区：打印/跨时区
def naive():      return datetime.now(CST).replace(tzinfo=None)  # 北京墙钟：与字符串算术
def ts():         return time.time()
def fmt_hms():    return now().strftime("%H:%M:%S")
def fmt_full():   return now().strftime("%Y-%m-%d %H:%M:%S")
```

**为什么保留 `naive()`**：`cron.compute_next` 和 `extract.parse_time` 大量用
`datetime.strptime()` 得到 naive 值再相减，直接换成 aware 会 `TypeError`。
「naive 但值是北京时间」是零结构改动的修法。

**顺带统一一个已有的死代码**：`bot/ports/clock.py` 里定义了 `Clock` 协议和
`default_clock()`，但**全项目没人用**。v18.0 顺手二选一：
要么让 `core/clock.py` 成为唯一实现并删掉 ports 那份，要么让 ports 的协议成为接口。
（建议前者：一个时钟不需要两套抽象。）

### L13 结论：不修（命令优先级最高）

原以为是 bug，实际是**有意的设计**：

| 消息类型 | 优先级 | 为什么 |
|---|---|---|
| 命令（`!version` 等） | **最高** | 你敲命令是想立刻知道结果，排在三条气泡后面 6 秒不可接受 |
| 普通回复 | 普通 | 分条发送本来就有节奏 |

所以「命令回复插进气泡中间」是**正确的**：

```
气泡1
气泡2
命令回复   ← 立刻响应
气泡3
```

**结论**：出站串行队列**不做**。如果以后觉得吵，正确做法是
「命令回复前先打断未发完的气泡」，而不是给所有消息排队。

### L18 说明：全角 `！` 不是命令

中文输入法（尤其手机）默认打出的是全角标点：

| 你打的 | 字符 | 现在的结果 |
|---|---|---|
| `!version` | 半角 `!` U+0021 | ✅ 识别 |
| `！version` | 全角 `！` U+FF01 | ❌ 当成聊天 |

**修法：命令解析前归一化**

```python
_FULL2HALF = str.maketrans({
    "！": "!", "：": ":", "，": ",", "；": ";", "？": "?",
    "（": "(", "）": ")", "　": " ",
})

def normalize_command(text):
    return (text or "").translate(_FULL2HALF).strip()
```

**三条规则**

| 规则 | 说明 |
|---|---|
| 只归一化命令相关字符 | 不改正文，避免影响记忆/情绪判断 |
| 归一化在最外层做一次 | `handle_command` 入口，后续都用归一化后的串 |
| 日志保留原文 | 便于排查到底打的是哪个符号 |

**顺带**：`!cron add 07：30`（中文冒号）也该能认。

**验收**

```

```


**根因**：`shutdown_event.set()` 只是把旗子立起来，**没有任何循环在等它**：

| 组件 | 有没有看这个事件 |
|---|---|
| `app/loop.py` 的 `serve()` | 有，但它在 `async with websockets.serve(...)` 里等，退出时会因异常重进循环（还带重启熔断） |
| 调度器 worker | ❌ 不看 |
| idle / proactive tick | ❌ 不看 |
| 心跳 | ❌ 不看 |

所以进程该跑还跑。

**修法（退出三步走）**

```python
async def graceful_exit():
    # 1. 停掉所有会再发消息的东西
    scheduler.shutdown()          # 取消 worker 与队列
    cron.cancel_all()             # 取消定时钩子
    for t in asyncio.all_tasks():
        if t is not asyncio.current_task():
            t.cancel()

    # 2. 关门
    await ws.close()
    txtlog.flush()                # 落盘

    # 3. 看门狗：5 秒还没退，硬退
    asyncio.get_event_loop().call_later(5, os._exit, 0)
```

**两条纪律**

| 纪律 | 原因 |
|---|---|
| 退出**必须**有硬兜底（`os._exit`） | 依赖协程全部优雅结束不可靠 |
| 退出时**先取消再关连接** | 否则取消过程中还在往外发消息 |

```

```

**为什么用 epoch 而不是库的 `NOW()`**

| 做法 | 结果 |
|---|---|
| `TIMESTAMPDIFF(SECOND, first_start, NOW())` | MySQL 服务器时区常是 UTC，`first_start` 是东八区字符串 → **多 8 小时**（L11 同源） |
| `UNIX_TIMESTAMP() - first_start_ts` | 两边都是 epoch，**与时区无关** |

**方言坑**

- SQLite 没有 `UNIX_TIMESTAMP()` / `UNSIGNED` / `SIGNED` / `CREATE OR REPLACE VIEW`
- `_adapt_view()` 逐个翻译；SQLite 先 `DROP VIEW` 再建 → **老库的旧视图会升级**
- 视图 SQL 里**不能出现 `%s`**：`_SQLiteCursor` 会把它当占位符换成 `?`（所以用 `julianday('now') - 2440587.5` 算 epoch）

**实测（真实库副本，2026-11-12）**

```

清空后 uptime: 0天0小时14分钟 | first_start: 2026-11-12 13:25:08 | source: view
```

老库（只有 `first_start`、没有 `first_start_ts`）在启动时自动补 epoch，视图从 `NULL` 变成可读。

**测试**：`tests/test_meta.py` 15 条（临时库隔离 / 清空 logs 不归零 / 老库补 epoch / 视图方言 / 老视图重建 / `!uptime` 与 `!meta`）。

## v18.6 · 引用上下文（1 天）✅ 已完成

> **只做一件事**：她得看见「被引用的原话」，而且不能为每条引用白等 8 秒。

| 环节 | 实际情况 |
|---|---|
| 接收 | `websocket_handle_qq` 在 `while True: raw = await ws.recv()` 里**直接 await** `_handle_message` |
| 取引用 | `parse_message_content` 又 `await request_action("get_msg")`，等的是**同一条 ws** 的 echo 回包 |
| 死结 | 唯一能读回包的 recv 循环正卡在 `_handle_message` 里 → 回包永远读不到 → 8 秒超时 |


**三个连带伤害**

| 伤害 | 说明 |
|---|---|
| 慢 | 每条引用白等 8 秒才进模型；`get_msg` 期间整个 recv 循环停摆，连发合并也收不到后两句 |

### L6 方案：元数据表 + 视图解耦

**第一步：表（存事实）**

```sql
CREATE TABLE bot_meta (
    key_name   VARCHAR(64) PRIMARY KEY,
    value      TEXT NOT NULL,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
-- 首次启动写一次，之后只读
-- INSERT IGNORE INTO bot_meta(key_name, value) VALUES('first_start', NOW());
```

**第二步：视图（给查询层用的稳定接口）**

```sql
CREATE VIEW v_bot_meta AS
SELECT
    key_name,
    value,
    updated_at,
    CASE key_name
        WHEN 'first_start' THEN DATEDIFF(NOW(), value)      -- 天数（MySQL）
        ELSE NULL
    END AS days_since
FROM bot_meta;
```

**第三步：代码只认视图**

```python
# infra/repo_meta.py（新）
def uptime_days(cursor=None):
    c = cursor or get_cursor()
    c.execute("SELECT days_since FROM v_bot_meta WHERE key_name='first_start'")
    ...
```

| 层 | 谁在用 | 能改吗 |
|---|---|---|
| `bot_meta` 表 | 只有 `repo_meta` 写 | 结构可变，视图负责兜住 |
| `v_bot_meta` 视图 | `repo_meta` 读、命令层读 | **对外契约**，改要同步 |
| 命令层 | 只调 `repo_meta.uptime_days()` | 不碰 SQL |

**为什么用视图而不是直接读表**

1. **换存储不用改代码**：以后 `first_start` 从 MySQL 挪到 SQLite/文件，
   只改视图定义，`repo_meta` 和命令层不动
2. **算天数有方言**：MySQL 用 `DATEDIFF`，SQLite 用
   `julianday('now') - julianday(value)`——**视图里吃掉方言**，
   上层拿到的永远是「天数」这个统一语义
3. **可加派生字段**：以后想看「运行几小时」「首次启动是周几」，
   加进视图即可，不动表

**方言适配要补一块**

`infra/schema.py` 现在只管 `CREATE TABLE`，要加 `VIEWS` 字典 +
`adapt_ddl(..., kind="view")`，把 `DATEDIFF(NOW(), x)` 翻成
`CAST(julianday('now') - julianday(x) AS INTEGER)`。
