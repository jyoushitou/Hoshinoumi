# v19 系列 · 多用户后端 API（把能力做成服务）

> 前置：v17（出站层 / 调度）、v18（记忆分量）｜预估 9 天｜**四个次版本**
>
> 现在所有能力都长在「QQ 消息处理」这一条路径上：
> 想从网页或手机用，只能假装发一条 QQ 消息。
> **这一版把能力拆出来，变成可被任意客户端调用的 API。**
>
> **注意分工**：v19 只做「内部业务接口」，**不做鉴权、不做公网入口**——
> 那些是 v20 网关的事。

## 为什么先做 API 而不是直接做网关

```
            ┌──────────── 没有 v19 ────────────┐
  Web/App → │ 直接连 botv 内部函数（想到就调） │  ← 耦合、没法限流、没法鉴权
            └──────────────────────────────────┘

            ┌──────────── 有 v19，v20 再加网关 ────────────┐
  Web/App → │ 网关（鉴权/限流） → API（业务） → botv 核心  │
            └──────────────────────────────────────────────┘
```

**先有业务接口，才有东西可保护。** 顺序不能反。

## 这一版做四件事

| 做 | 不做（留给 v20） |
|---|---|
| **多用户底座**：`users` / `identities` / `roles` + `user_id` 隔离 | 登录、JWT、密码 |
| 定义 API 契约（路径、入参、出参） | 限流、IP 白名单 |
| 内部 HTTP 服务（只听 127.0.0.1） | HTTPS、域名、公网暴露 |
| 复用现有逻辑：聊天、历史、状态（按 user） | 跨用户聚合/管理后台 |

## 多用户模型（v19 起）

> 从这一版起不再假设 `MASTER_QQ` 是唯一用户。所有接口、表、查询都带 `user_id`。

| 概念 | 定义 |
|---|---|
| `user_id` | 账号/租户：一个人类用户 |
| `identity` | 绑定到 user 的渠道身份：QQ 号 / Web 账号 / 桌面设备 / 手机 |
| `target_id` | 会话：私聊 = `user_id`；群 = 群号；Web = `thread_id` |
| `role` | `owner` / `admin` / `user` |

**规则**：

- 每个请求必须带 `user_id`；没有「不传就是主人」的默认。
- v19 仍不做登录（v20 做），但只信任**本机/网关**传入的 `user_id`；本机直连按 owner。
- 每张业务表、每个查询按 `user_id` 隔离；群聊用 `speaker_id` 区分发言人。
- QQ 私聊首次消息自动建 `user`（role=user），owner 可封禁；群聊归 owner/租户。
- 存量数据迁移时全部回填到 owner。
- **验收红线**：两个用户互相看不到对方的记忆、历史、日程、日记、书架。

## 接口契约（初版）

```
POST /internal/chat          {user_id, target_id, text} → {reply, bubbles}
GET  /internal/history?user_id=&target_id=&limit=&before= → {messages[]}
GET  /internal/state?user_id=                 → {mood, energy, relation, reading}
GET  /internal/cron?user_id=                  → {tasks[]}
POST /internal/cron/add      {user_id, ...}    → {id}
GET  /internal/diary?user_id=&limit=          → {entries[]}
GET  /internal/shelf?user_id=                 → {books[]}
```

**约定**：

- 全部返回 JSON，统一 `{ok, data, error}` 包装
- `user_id` **必填**，没有「不传就是主人」；本机直连按 owner
- `target_id` 是会话：私聊 = `user_id`，群 = 群号，Web = `thread_id`
- **不带鉴权**（只听本机），调用方必须是本机进程（网关）；网关负责填 `user_id`

## 序列化：网关 ↔ 后端用 Protobuf（gRPC）

> 客户端（Web/App）仍然说 **JSON**；但**网关到后端**这一段改用
> **Protobuf over gRPC**。原因：类型强、体积小、跨语言、自带版本规则。

```
Web/App  ──JSON/REST──▶  网关  ──gRPC/protobuf──▶  后端 API  ──▶  botv
```

### 为什么这一段值得用 protobuf

| 点 | JSON | Protobuf |
|---|---|---|
| 契约 | 靠文档约定 | **`.proto` 就是契约**，改字段会编译报错 |
| 类型 | 什么都是字符串 | int/float/enum 明确 |
| 体积 | 大（尤其历史消息分页） | 小 30~50% |
| 跨语言 | 手写解析 | `protoc` 生成 Go/Python/Dart/TS |
| 兼容 | 加字段可能炸客户端 | 字段号不变就兼容 |

**结论**：客户端对外用 JSON（好调试、浏览器原生），
内部这一段用 protobuf（严谨、快）。

```bash
    proto/nao/v1/*.proto
```

**生成物要提交**：别人 clone 下来不用装 protoc 也能跑。

### 消息定义（初版）

```protobuf
syntax = "proto3";
package nao.v1;

message ChatRequest {
  string user_id   = 1;          // 账号/租户，必填
  string target_id = 2;          // 会话：私聊=user_id，群=群号，Web=thread_id
  string text      = 3;
}
message ChatReply {
  string reply     = 1;
  repeated string bubbles = 2;   // 分条后的每条
  bool   ok        = 3;
  string error     = 4;          // ok=false 时填
}
message HistoryRequest {
  string user_id   = 1;
  string target_id = 2;
  int32  limit     = 3;
  int64  before_ts = 4;          // 毫秒时间戳，0 表示最新
}
message Message {
  string role      = 1;          // user / bot
  string text      = 2;
  int64  ts        = 3;
}
message HistoryReply {
  repeated Message messages = 1;
  bool  has_more = 2;
}
service ChatService {
  rpc Chat(ChatRequest) returns (ChatReply);
  rpc History(HistoryRequest) returns (HistoryReply);
}
```

### 错误码（统一）

| gRPC code | 含义 | 网关转 HTTP |
|---|---|---|
| `OK` | 成功 | 200 |
| `INVALID_ARGUMENT` | 参数错 | 400 |
| `UNAUTHENTICATED` | 没带 token | 401 |
| `PERMISSION_DENIED` | token 无效 | 403 |
| `RESOURCE_EXHAUSTED` | 限流 | 429 |
| `INTERNAL` | 模型/数据库错 | 500 |

**这一节从 v19.1 就开始做**：先定 proto，再写实现。
骨架阶段就能 `protoc` 编译通过、起一个空 gRPC 服务。

### 验收（v19.1 加一条）

```bash
python -m grpc_tools.protoc -I proto --python_out=/tmp proto/nao/v1/*.proto \
  && echo "proto 编译通过"
python -m grpc_tools.protoc -I proto --grpc_python_out=/tmp proto/nao/v1/*.proto
```

## 红线

| 红线 | 原因 |
|---|---|
| **只监听 127.0.0.1** | 没有鉴权，绝不能对外 |
| **不实现鉴权** | 那是 v20 的事，混在一起会做两遍 |
| **不带 `user_id` 直接拒绝** | 不允许「不传就是主人」的默认 |
| **禁止跨用户查询** | 仓储层强制过滤；跨用户返回 403/404 |
| 不复制业务逻辑 | 只做「参数转换 + 调用现有函数」，逻辑仍在 botv 里 |

## 验收（系列整体）

```bash
curl -s 'localhost:7070/internal/state?user_id=owner' | python3 -m json.tool
curl -s -X POST localhost:7070/internal/chat \
     -H 'Content-Type: application/json' \
     -d '{"user_id":"owner","target_id":"822891053","text":"在吗"}'
```

| 项 | 标准 |
|---|---|
| 能聊 | 返回的话和 QQ 里一致 |
| 能查 | 历史/状态/日记/书架都能读 |
| 多用户 | A 的 `user_id` 看不到 B 的任何数据 |
| 不越权 | 非本机地址连不上；缺 `user_id` 400 |
| 无鉴权 | 明确「v20 才做」；v19 只信任本机/网关 |

## 与 v20 / v21 / v22 的关系

```
v19 后端 API（内部接口，按 user 隔离）
   ↓ 交给
v20 网关（唯一入口：鉴权 / 限流 / TLS / 路由，JWT sub=user_id）
   ↓ 服务
v22 电脑 Web    v25 手机 App    v23/v24 桌面端
```

**加客户端时，只改网关后面的路由，API 不动。**
