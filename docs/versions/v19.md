| 版本 | 主题 | 风险 | 预估 |
|---|---|---|---|
| **v19.0.0** | bash 模式（只读命令） | 中 | 2 天 |

# v19.0.0 · bash 模式（只读）

> 前置：v17（命令通道 + 线程化）｜预估 2 天｜**风险最高的一版，默认关闭**

## 目标

主人在 QQ 里说一句，就能**查**服务器状态、看日志、看进程——不用 SSH。

**只读，不写**：这一版不做任何会改变系统的操作。

```
你：看下磁盘
她：（执行 df -h）根分区用了 78%，还有 12G

你：后端日志最后 20 行
她：（执行 journalctl/tail）最近 20 行是……
```

## 为什么危险

这等于**把服务器 shell 接到 QQ 上**。风险点：

| 风险 | 后果 |
|---|---|
| QQ 号被盗 | 对方拿到服务器控制权 |
| 模型理解错 | 「清理一下磁盘」→ 执行了 `rm` |
| 命令注入 | 自然语言里的分号/管道被拼进命令 |
| 输出过大 | 一次 `cat` 大文件把 bot 卡死 |
| 长命令 | `sleep 600` 占住 worker |

所以这一版**安全设计比功能重要**。

## 设计：白名单，不是自由 shell

**不做**「把你说的话直接丢给 bash」。做**命令白名单**：

```python
# 只读运维命令：查状态，不改任何东西
COMMANDS = {
    # 系统资源
    "disk":    ["df", "-h"],
    "mem":     ["free", "-m"],
    "load":    ["uptime"],
    "cpu":     ["top", "-bn1", "-o", "%CPU"],          # 只取一帧
    "ps":      ["ps", "-eo", "pid,pcpu,pmem,comm", "--sort=-pcpu"],
    # 进程与服务
    "service": ["systemctl", "status", "{name}", "--no-pager", "-l"],
    "ports":   ["ss", "-tulnp"],
    # 日志（只读，tail 限定行数）
    "log":     ["tail", "-n", "{n}", "{file}"],
    "journal": ["journalctl", "-u", "{name}", "-n", "{n}", "--no-pager"],
    # Docker（只读）
    "docker":  ["docker", "ps", "--format", "{{.Names}}\t{{.Status}}"],
    "dlogs":   ["docker", "logs", "--tail", "{n}", "{name}"],
    # 代码仓库（只读）
    "git":     ["git", "-C", "/app", "status", "--short"],
    "gitlog":  ["git", "-C", "/app", "log", "--oneline", "-n", "{n}"],
    # 基础信息
    "uname":   ["uname", "-a"],
    "date":    ["date"],
}
```

| 规则 | 说明 |
|---|---|
| 只执行白名单里的命令 | 不在表里的一律拒绝 |
| 参数用**正则校验** | `{n}` 只能是 1~200 的数字；`{file}` 只能是白名单路径 |
| **不经过 shell** | `subprocess.run(argv, shell=False)`，天然免疫 `;` `|` `&&` 注入 |
| 输出截断 | 最多 1500 字，超出加「…（已截断）」 |
| 超时 | 20 秒，超时 kill |
| 降权 | 以 bot 用户运行，**不给 sudo** |
| 审计 | 每条命令 + 输出摘要写日志和数据库 |
| 频率 | 每分钟最多 5 条 |
| 默认关闭 | `NAO_SHELL=1` 才启用 |
### 禁止清单（写死在代码里，不在白名单就执行不了）

| 类别 | 例子 | 为什么禁 |
|---|---|---|
| 重启/停止服务 | `systemctl restart`、`docker restart` | 会中断机器人在跑 |
| 文件增删改 | `rm`、`mv`、`cp`、`>` 重定向 | 一误操作就没了 |
| 杀进程 | `kill`、`pkill` | 可能杀掉自己 |
| 装包/改系统 | `apt`、`pip install`、`systemctl enable` | 改变环境 |
| 交互式 | `vim`、`top`（无 `-b`）、`less` | QQ 里没法交互 |
| 网络探测 | `curl`、`wget`、`nc` | 可被用来打内网 |
| 提权 | `sudo`、`su` | 出事没有边界 |

**这一版只做「看」，不做「改」**——查状态、看日志、看进程。想改东西还是 SSH 上去。


## 自然语言怎么接

**两种模式，默认只用第一种**：

| 模式 | 说明 | 风险 |
|---|---|---|
| **A. 命令名 + 参数** | 「看磁盘」→ 匹配关键词 → `disk` → `df -h` | 低 |
| B. 模型自由生成命令 | 模型输出完整命令行 | **高，默认不开** |

模式 A 的实现：关键词表 + 模型只在**白名单里选**（不给它写命令的权限）：

```python
# 模型只输出一个 key，不输出命令
{"action": "disk"}     # → 查表得到 ["df", "-h"]
```


## bash 模式（进出与鉴权）

和「代码模式」同一套交互习惯：`!bash` 进入、`!bash off` 退出、闲置自动退出。
但**多一道鉴权**——因为这条通道能摸到服务器。

### 状态机

```
        !bash <鉴权码>
休眠 ─────────────────→ 已进入（10 分钟倒计时）
  ↑                          │
  │  !bash off / 超时 / 进程重启 / 鉴权失败超限
  └──────────────────────────┘

鉴权失败 3 次 → 锁定 10 分钟（期间不再接受进入请求）
```

### 进入

```
你：!bash 2468
她：🔧 已进入 bash 模式（只读运维）
    可以问：磁盘、内存、负载、服务状态、日志
    10 分钟无操作自动退出，!bash off 退出

你：看下磁盘
她：根分区 78%，剩 12G
```

### 鉴权

| 项 | 说明 |
|---|---|
| 鉴权码来源 | `config.local.json` 的 `bash_key`，或环境变量 `NAO_BASH_KEY` |
| 校验方式 | 常数时间比较，防时序侧信道 |
| 失败处理 | 拒绝 + 计数；**3 次失败锁 10 分钟** |
| 未配置鉴权码 | bash 模式**永远进不去**（不是默认放开） |
| 群里 | **禁止在群里进入**，只允许私聊 |

### 进入时必贴：免责声明 + 实现逻辑

每次进入都要贴（不是首次才贴），**不能跳过、不能省略**。

```
⚠️ bash 模式（只读运维）

【免责声明】
本功能会以机器人进程的权限在你的服务器上执行命令。
虽然只开放只读白名单、不走 shell，但仍可能因误判、
配置错误或账号被盗导致信息泄露。
继续使用即表示你理解并自行承担风险。

【实现逻辑】
1. 只执行白名单命令（df/free/uptime/log/docker ps 等 15 个）
2. 不经过 shell（shell=False），分号/管道注入无效
3. 参数经正则校验；输出截断 1500 字；超时 20 秒
4. 只读：不改文件、不改服务、不装包
5. 每条命令都写审计日志
6. 10 分钟无操作自动退出；!bash off 手动退出

已进入。可以问：磁盘 / 内存 / 负载 / 服务状态 / 日志
```

| 规则 | 说明 |
|---|---|
| 每次进入都贴 | 不缓存、不省略 |
| 贴在「已进入」之前 | 先看风险，再给能力 |
| 日志留痕 | 贴出免责声明这件事本身也记审计 |
| 不可配置关闭 | 没有「不再提示」选项 |

### 进入后的消息怎么处理

```
普通文本 → 关键词匹配 → 命中白名单 → 执行 → 返回结果
                      → 没命中   → 「这个我不能查（不在白名单）」
```

**完全不经过模型**——避免模型「理解」出白名单外的命令。

| 输入 | 处理 |
|---|---|
| 「看下磁盘」 | 关键词命中 `disk` → `df -h` |
| 「后端日志最后 20 行」 | 命中 `log`/`journal`，参数校验 20 |
| 「重启后端」 | 命中禁止词 → 「只能查看，不能修改」 |
| 「今天吃什么」 | 不在白名单 → 「bash 模式只做只读运维，聊天请先 !bash off」 |
| `!` 开头的命令 | 照常走命令通道（`!bash off` 等） |

### 退出条件

| 条件 | 说明 |
|---|---|
| `!bash off` | 手动退出 |
| 10 分钟无操作 | 自动退出（比代码模式的 30 分钟短） |
| 进程重启 | 状态不持久化，重启后回到休眠 |
| 鉴权失败超限 | 锁定期内视为未进入 |

### 与代码模式的区别

| | 代码模式 `!code` | bash 模式 `!bash` |
|---|---|---|
| 鉴权 | 无（仅主人） | **要鉴权码** |
| 能做什么 | 回答问题（知识优先） | 执行白名单只读命令 |
| 走模型 | 是 | **否**（关键词直匹配） |
| 自动退出 | 30 分钟 | **10 分钟** |
| 群里可用 | 是 | **否** |
| 审计 | 无 | **每条都记** |

### 审计

每条执行都写 `events(kind='ops')`：

```
时间 | 原始输入 | 匹配到的命令 | 参数 | 退出码 | 输出摘要(≤120字) | 是否拒绝
```

被拒绝的尝试**也要记**——这样被盗号时能看出对方在试探什么。

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `bash_key` | 空（不允许进入） | 鉴权码，放 `config.local.json` |
| `bash_idle_min` | 10 | 无操作自动退出（分钟） |
| `bash_fail_limit` | 3 | 连续鉴权失败上限 |
| `bash_lock_min` | 10 | 锁定时长（分钟） |

## 与 v17 系列的关系

| 依赖 | 为什么 |
|---|---|
| v17.0 并发基础 | 命令执行走专用线程，不阻塞事件循环 |
| v17.2 命令通道 | 这本质是命令，必须绕过 worker 池（池满也要能用） |

## 全局参数（进程级）

| 参数 | 默认 | 说明 |
|---|---|---|
| `shell_enabled` | false | 总开关（`NAO_SHELL=1`） |
| `shell_timeout` | 20 | 单条命令超时（秒） |
| `shell_output_max` | 1500 | 输出截断长度 |
| `shell_rate` | 5 | 每分钟最多几条 |
| `shell_readonly` | true | 强制只读（本版恒为 true，不提供关闭选项） |

## 验收

- [ ] 「看磁盘」能返回 `df -h` 结果
- [ ] 不在白名单的命令被拒绝（回「这个我不能执行」）
- [ ] 注入尝试（`df -h; rm -rf /`）被拒绝——因为参数校验过不了
- [ ] 输出超长自动截断
- [ ] 超时命令被 kill
- [ ] 非主人发命令**完全无响应**（不提示、不报错）
- [ ] `restart`/`rm`/`apt` 这类命令被明确拒绝（回「只能查看，不能修改」）
- [ ] `!bash` 不带给权码进不去；错 3 次锁 10 分钟
- [ ] 群里发 `!bash` 被拒绝（只能在私聊）
- [ ] 进入后 10 分钟无操作自动退出
- [ ] 每条执行都进审计日志

## 红线（写死在代码里）

| 红线 | 原因 |
|---|---|
| 不用 `shell=True` | 免疫注入 |
| 不给 sudo | 出事也有边界 |
| 不开放文件写入/删除类命令 | 只读优先 |
| 不做交互式命令（vim/top） | 无法在 QQ 里交互 |
| 非主人零响应 | 不给探测机会 |
| 默认关闭 | 想用的人自己开 |

## 风险提示

即使做了上面所有事，**QQ 号被盗 = 服务器被看光**。所以：

- 只读命令为主（df/free/uptime/log tail）
- 建议配合 QQ 的设备锁/登录保护

# v19.1.0 · agent 模式（只读）

> 前置：v19（只读白名单执行器）｜预估 3 天｜**风险第二高，默认关闭**

## 目标

你说一句「怎么又挂了」，她**自己去看**：查进程、看日志、看内存，然后告诉你结论。

```
你：!agent 2468
她：🤖 Agent 模式（只读运维）
    你说问题，我自己去查。10 分钟无操作自动退出。

你：机器人好像不回消息了
她：（查进程）→（看日志）→（看内存）
    进程还在，但日志里 12:03 开始一直报数据库连接超时，
    内存用了 92%，可能是 MySQL 那边的问题。
```

和 v19 的区别：

| | v19 bash 模式 | v20 agent 模式 |
|---|---|---|
| 谁决定查什么 | **你**（关键词匹配） | **她**（模型规划） |
| 执行几轮 | 1 轮 | 最多 5 轮 |
| 输出 | 命令原文 | 结论 + 依据 |
| 风险 | 中 | **中高**（模型可能乱查） |

## 核心设计：她只能调工具，不能写命令

**关键约束**：模型不生成 shell，只生成**工具调用**。

```json
{"tool": "log", "args": {"file": "/app/bot.log", "n": 50}}
```

代码侧：
1. 查白名单 → 得到 argv
2. 参数校验（`shell=False`）
3. 执行、截断输出
4. 把结果喂回模型
5. 最多 5 轮，然后必须给结论

**模型永远碰不到 shell**（和 v19 共用同一个执行器）。

## 模式进出

| 项 | 规则 |
|---|---|
| 进入 | `!agent <鉴权码>`（和 `bash_key` 共用，或单独的 `agent_key`） |
| 退出 | `!agent off` |
| 自动退出 | 10 分钟无操作 |
| 群里 | **禁止**，只允许私聊 |
| 与 bash 模式 | **互斥**：进入 agent 自动退出 bash，反之亦然 |
| 未配置 key | 永远进不去 |

## 鉴权（和 bash 模式同一套机制）

两个模式都要鉴权，**共用同一套逻辑**，只是计数分开。

| 项 | 规则 |
|---|---|
| 鉴权码来源 | `config.local.json` 的 `agent_key`（独立），没配就退回 `bash_key` |
| 都没配 | **永远进不去**（不是默认放开） |
| 校验方式 | 常数时间比较（`hmac.compare_digest`），防时序侧信道 |
| 失败处理 | 拒绝 + 计数；**连续 3 次失败锁 10 分钟** |
| 锁定期内 | 不再校验、不再响应，只回一句「已锁定」 |
| 成功进入 | 清零失败计数 |
| 群里 | **禁止进入**，只接受私聊 |
| 审计 | 进入成功/失败都记 `events(kind='ops')`，含 QQ 号、时间、结果 |

### 和 bash 模式的互斥

```
!agent 2468  → 退出 bash（如果在），进入 agent
!bash 2468   → 退出 agent（如果在），进入 bash
```

两个模式**不能同时存在**——避免「以为在 bash，其实 agent 拿着工具在跑」。

### 进入时的会话

每次进入生成一个 `session_id`：

```
session_id = f"{qq}-{int(time.time())}-{random4}"
```

作用：

- 审计里能串起「这次会话都干了什么」
- 超时退出时按 session 收尾
- 错误信息里带上 session，方便排查

### 鉴权失败的样子

```
你：!agent 0000
她：❌ 鉴权失败（还可尝试 2 次）

你：!agent 0000
她：❌ 鉴权失败（还可尝试 1 次）

你：!agent 0000
她：🔒 已锁定 10 分钟（连续 3 次失败）
```

**锁定期间任何口令都不再校验**——防止用锁定当探测器穷举。

### 进入时必贴：免责声明 + 实现逻辑

```
⚠️ Agent 模式（只读运维）

【免责声明】
本模式下模型会自己决定查什么，并以机器人进程的权限
在你的服务器上执行命令。
虽然只开放只读白名单、不走 shell、有轮数限制，
但仍可能因模型误判导致查询方向错误或信息泄露。
继续使用即表示你理解并自行承担风险。

【实现逻辑】
1. 模型只能从只读白名单里选工具，**不能写命令**
2. 最多 5 轮工具调用；单轮输出截断 1500 字；总超时 60 秒
3. 不经过 shell（shell=False），注入无效
4. 只读：没有重启/删除/安装类工具
5. 每一轮工具调用都写审计日志（带 session_id）
6. 结论必须引用工具输出，查不清就说查不清
7. 10 分钟无操作自动退出；!agent off 手动退出

已进入。说说哪里不对，我自己去查。
```

| 规则 | 说明 |
|---|---|
| 每次进入都贴 | 和 bash 模式一致 |
| 明确「模型决定」 | 让用户知道不是关键词匹配 |
| 明确「最多 5 轮」 | 预期管理 |
| 明确「查不清就说查不清」 | 降低幻觉被当成事实的概率 |

## Agent 循环

```
用户的话
   ↓
[模型] 决定调用哪个工具（或直接回答）
   ↓ 有工具调用
[执行器] 白名单 → argv → 执行 → 截断
   ↓
[模型] 看结果，决定下一步（最多 5 轮）
   ↓ 没工具调用 / 轮数用完
给出结论
```

| 限制 | 值 | 原因 |
|---|---|---|
| 最大轮数 | 5 | 防止无限查 |
| 单轮输出预算 | 1500 字 | 防止撑爆上下文 |
| 总耗时 | 60 秒 | 防止卡住 |
| 总输出预算 | 6000 字 | 控制 token |

## 提示词要点（写死）

```
你是运维助手。你只能通过提供的工具查看服务器状态。
规则：
1. 不要编造命令或输出。看到什么说什么。
2. 每次只调用一个工具，等结果再决定下一步。
3. 不能做任何修改操作（重启/删除/安装）——你没有这些工具。
4. 最多 5 步。查不清就直说「查不出来，可能需要 SSH」。
5. 结论里要说明依据（哪个命令的输出）。
```

## 安全

| 措施 | 说明 |
|---|---|
| 只读白名单 | 复用 v19 的 `COMMANDS`，没有写操作 |
| 不生成 shell | 模型只输出工具名 + 参数 |
| 轮数/时间/输出三重上限 | 防跑飞 |
| 审计 | 每一轮工具调用都记 `events(kind='ops')`，带 `session_id` |
| 失败即停 | 工具连续失败 2 次 → 终止并报告 |
| 与 bash 互斥 | 避免状态混乱 |

## 涉及文件

# v19.2.0 · 有限写命令（强制备份）

> 前置：v19（只读执行器）+ v20（agent）｜预估 2 天｜**默认关闭**

## 目标

先放开**最常用、后果可控**的几个写命令，但每次执行前**必须备份**。

```
你：把服务重启一下
她：即将执行 docker restart nao-bot
    已备份：容器状态 + 当前日志尾部 → backups/20261110-1432/
    回复「确认」执行

你：确认
她：✅ 已重启。容器状态：Up 3 seconds
```

## 为什么先只开这几个

| 命令 | 后果 | 为什么敢开 |
|---|---|---|
| `docker restart <容器>` | 服务短暂中断 | 状态可查、失败可再拉起 |
| `systemctl reload <服务>` | 重载配置，不中断 | 比 restart 温和 |
| 轮转日志（`truncate`/rename） | 释放磁盘 | 原文件先备份 |
| 清空缓存目录（指定路径） | 缓存重建 | 路径白名单 + 先备份 |

**不开**：`rm` 任意文件、`apt`、`/etc` 修改、DDL、防火墙。

## 写命令白名单

```python
WRITE_COMMANDS = {
    "restart":  ["docker", "restart", "{name}"],          # name 必须在容器白名单
    "reload":   ["systemctl", "reload", "{name}"],        # name 必须在服务白名单
    "rotate":   ["mv", "{file}", "{file}.{ts}"],          # 只允许移动日志文件
    "clearcache": ["find", "{dir}", "-mindepth", "1", "-delete"],  # dir 必须在白名单
}
```

| 约束 | 说明 |
|---|---|
| `{name}` | 只能取预配置列表里的值（`nao-bot`、`mysql` 等） |
| `{file}` | 只能是 `logs/` 下的文件 |
| `{dir}` | 只能是 `data/cache` 这类指定目录 |
| 仍然 `shell=False` | 注入无效 |

## 强制备份（本版核心）

**备份失败 = 拒绝执行**，没有例外。

| 命令 | 备份什么 |
|---|---|
| `restart` | `docker inspect` 快照 + 最近 200 行日志 |
| `reload` | 服务状态 + 当前配置文件副本 |
| `rotate` | 原日志文件（移动前先 copy） |
| `clearcache` | 目录清单 + 文件总大小（不备份内容，太大） |

备份目录：

```
data/backups/20261110-1432/
  manifest.json      # 命令、时间、备份内容、执行结果
  state.json         # 服务/容器快照
  app.log.tail       # 日志尾部
```

## 二次确认

```
她：即将执行 <命令>，已备份到 <id>
    回复「确认」在 60 秒内生效，其他内容视为取消
```

| 规则 | 说明 |
|---|---|
| 确认词 | 精确匹配「确认」 |
| 有效期 | 60 秒 |
| **agent 模式** | 同样要确认，模型不能自批 |
| 取消 | 其他消息或超时 |

## 与 v22 的分工

| | v21（本版） | v22 |
|---|---|---|
| 范围 | 4 个写命令 | 完整分级（W1–W4） |
| 备份 | 有（单次快照） | 有（体系化 + 保留策略） |
| 回滚 | **不做**（手动看备份） | `!rollback` 一键回滚 |
| 确认 | 有 | 有 |

**v21 只保证「出事有东西可查」，v22 才保证「一键回去」。**

## 参数

| 参数 | 默认 | 说明 |
|---|---|---|

| `write_confirm_sec` | 60 | 确认有效期 |
| `write_names` | `nao-bot,mysql` | 允许操作的容器/服务名 |
| `write_log_dir` | `logs` | 允许轮转的日志目录 |

## 验收

# v19.3.0 · 可写体系（分级 · 备份 · 回滚）

> 前置：v21（有限写命令）｜预估 3 天｜**最高风险，默认关闭**

## 原则

**先备份 → 再执行 → 可回滚**。三步缺一不可。

```
你：把日志级别改成 DEBUG
她：即将修改 config.local.json（log_level: INFO → DEBUG）
    已备份到 backups/20261110-1432/config.local.json
    回复「确认」在 60 秒内生效

你：确认
她：✅ 已修改。如需回滚：!rollback 20261110-1432
```

## 为什么不能直接放开

| 直接放开 | 后果 |
|---|---|
| `sed -i` 改错一行 | 配置坏了，机器人起不来 |
| 迁移脚本跑一半 | 数据半新半旧 |
| 重启失败 | 服务长时间不可用 |

**备份 + 回滚是让「写」变得可接受的前提。**

## 写操作分级

| 级别 | 操作 | 备份方式 | 回滚方式 |
|---|---|---|---|
| **W1** | 改配置文件（`config.local.json`、`data/tunables.json`） | 复制原文件 | 拷回原文件 |
| **W2** | 重启服务/容器 | 记状态快照（`docker inspect` / `systemctl status`） | 重新拉起旧容器/服务 |
| **W3** | 更新代码（`git pull` / 切 tag） | 记当前 commit hash | `git reset --hard <hash>` |
| **W4** | 数据库迁移 | **先 dump 相关表** | 用 dump 恢复 |

**不支持的**（永远禁止）：

| 禁止 | 原因 |
|---|---|
| `rm` / `mv` 任意文件 | 无法可靠回滚 |
| 改系统文件（`/etc/*`） | 影响面太大 |
| 装/卸软件包 | 副作用不可控 |
| 改数据库结构（手工 DDL） | 必须走迁移脚本 |
| 关防火墙/开端口 | 安全风险 |

## 备份实现

### 目录结构

```
data/backups/
  20261110-1432/
    manifest.json          # 这次改了什么、为什么、谁触发
    config.local.json      # 文件快照
    db_tables.sql          # 表 dump（W4 才有）
    service_state.json     # 服务快照（W2 才有）
```

`manifest.json`：

```json
{
  "id": "20261110-1432",
  "level": "W1",
  "session": "822891053-1762753920-ab12",
  "target": "config.local.json",
  "before": "INFO",
  "after": "DEBUG",
  "created_at": "2026-11-10 14:32:05",
  "restored": false
}
```

### 保留策略

| 项 | 值 |
|---|---|
| 最多保留 | 10 份 |
| 单份上限 | 50 MB（DB dump 单独限制） |
| 超限 | 删最旧的（**已回滚过的优先删**） |

### DB 备份

复用已有的 `scripts/backup_table.py`（v7 就写了，支持 `--restore --wipe`）。

```
python3 scripts/backup_table.py --table events --out data/backups/<id>/events.sql
```

## 回滚

```
!rollback <id>          # 回滚指定备份
!rollback last          # 回滚最近一次
!backups                # 列出可用备份
```

回滚流程：

```
读 manifest → 按 level 选恢复方式 → 执行 → 验证 → 标记 restored
```

| 级别 | 回滚动作 |
|---|---|
| W1 | 拷回文件 → 重启或热加载 |
| W2 | 用快照重新拉起旧容器 |
| W3 | `git reset --hard <hash>` → 重启 |
| W4 | 还原表 → 重启 |

## 二次确认（写操作必须）

```
她：即将修改 X（A → B），已备份到 <id>

```

| 有效期 | 60 秒 |
| 超时 | 自动取消，备份保留（可手动清理） |
| 取消 | 任何其他消息 |
| agent 模式 | **同样要确认**，模型不能自己确认 |
