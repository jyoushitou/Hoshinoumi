# v19 · 连发消息合并

> 前置：v6（节奏）+ v15（可调参数）｜预估 1~2 天

## 问题

现在**你连发三条，她就回三条**：

```
你：在吗
你：今天好累
你：不想动了

她：嗯在
她：怎么了
她：那就歇着
```

三个毛病：

| 问题 | 后果 |
|---|---|
| 上下文割裂 | 她回第一条时还不知道你后面说了什么 |
| 回复零碎 | 三句话拆成三次，像三个机器人在回 |
| 慢且贵 | 每条一次模型调用，延迟叠加 1.5~3 秒 ×3 |

## 目标

**2 秒内连发的消息算一条**，合并后只回一次。

```
你：在吗
你：今天好累
你：不想动了
        ↓ 2 秒内
她：在。今天怎么了，累成这样
```

## 为什么现在做不到

接收和处理在**同一个循环**里：

```python
while True:
    rs = await ws.recv()          # 收
    ...
    await get_character_reply()   # 处理（阻塞，此时收不到新消息）
```

处理的时候根本没在读 socket，所以看不到你后面发的话。

## 改造方案

### 1. 拆开「收」和「处理」

```python
while True:
    rs = await ws.recv()
    parse → cfg.msg_queue[tid].append(text)
    if tid not in workers: workers[tid] = asyncio.create_task(worker(tid))
```

### 2. 合并窗口（核心）

```python
async def worker(tid):
    await asyncio.sleep(MERGE_WINDOW)      # 2 秒，等你把话说完
    texts = drain(cfg.msg_queue[tid])      # 取走这段时间的全部
    merged = "\n".join(texts)
    ans = await get_character_reply(merged, tid)
```

### 3. 合并规则

| 情况 | 处理 |
|---|---|
| 2 秒内的 N 条 | 按顺序用换行拼起来，作为**一条**用户消息 |
| 超过 5 秒还在发 | 最多等 5 秒（防止一直等不到安静） |
| 期间夹了命令（`!` 开头） | 命令**单独立即处理**，不参与合并 |
| 期间夹了图片/语音 | 记录到同一条里（`[图]` 标记） |
| 单条消息 | 也要等 2 秒吗？→ **不用**：只有收到第二条时才启动窗口 |

### 4. 延迟的叠加问题

合并后仍要保留原有的「打字延迟」（1.5~3 秒）——**2 秒窗口 + 3 秒延迟 = 5 秒才回**，可以接受，但要确认：

| 组合 | 总延迟 |
|---|---|
| 单条消息 | 3 秒（不变） |
| 2 秒内连发 3 条 | 2 + 3 = 5 秒 |
| 一直发不停 | 5 + 3 = 8 秒（上限） |

如果觉得慢，把窗口调到 1.2 秒（参数化）。

## 参数（进 `!config`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `merge_window_ms` | 2000 | 连发合并窗口 |
| `merge_max_wait_ms` | 5000 | 最长等待 |
| `merge_enabled` | true | 总开关 |

## 涉及文件

- `botv/chat/handler.py`：接收循环拆成「入队 + worker」
- `botv/core/state.py`：`msg_queue` / `workers` / 合并参数
- `botv/core/tunables.py`：三个新参数
- `botv/chat/inbound.py`：合并后文本的标记（图片/语音占位）

## 验收

- [ ] 2 秒内连发 3 条 → 只回 1 次
- [ ] 回的内容**包含了三条的信息**
- [ ] 单条消息的延迟不变（不加 2 秒）
- [ ] `!` 命令不受影响，立即执行
- [ ] 图片/语音混在连发里，不丢信息
- [ ] 并发：两个不同的人同时发，各自合并、互不阻塞

## 风险

| 风险 | 处理 |
|---|---|
| 拆循环后并发变复杂 | 保留 per-target 锁，worker 内部串行 |
| 消息丢失（任务没起来） | 入队和起任务在同一段同步代码里 |
| 一直发不停导致不回复 | `merge_max_wait_ms` 硬上限 |
| 合并后太长超预算 | 已有分层预算会截断，无需额外处理 |

## 与已有机制的关系

| 机制 | 影响 |
|---|---|
| per-target 锁 | 保留，worker 内串行 |
| 消息去重（PROCESSED_MSG_IDS） | 保留，入队前判重 |
| 群聊闸门（3 秒间隔/6 条窗口） | 保留，作用于合并后的**一次**回复 |
| 记忆轮数（30 轮） | 合并后算**一轮**，不再拆成三轮 |
