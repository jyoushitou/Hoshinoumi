# v21 系列 · 网关（公网请求的唯一入口）

> 前置：v20（多用户后端 API + proto 已就绪）｜预估 12 天｜**三个次版本**
>
> **公网来的请求只走网关**：手机 4G、外面咖啡馆的 Wi-Fi、以后的小程序。
> 本机上的东西（DSH / Qoder 插件、自己的 Web 前端跑在同一台机器）**直连内部 API**，
> 不必绕一圈——省一跳延迟，也少一个失败点。

## 为什么必须有网关

| 没有网关 | 有网关 |
|---|---|
| 每个客户端自己写鉴权 | 一处鉴权，所有客户端受益 |
| 谁都能直连后端 | 只有网关能连后端 |
| 限流写在各处 | 统一限流 |
| 没有访问审计 | 每个请求都有记录 |
| 加客户端要改后端 | 只改网关路由 |

## 架构位置

```
   手机 App        电脑 Web        以后：小程序 / CLI
      │               │                  │
      └───────┬───────┴──────────────────┘
              ↓  HTTPS / WSS
   ┌──────────────────────────┐
   │  网关（v21）              │
   │  鉴权 · 限流 · 路由 · 审计 │
   └──────────┬───────────────┘
              ↓  只走 127.0.0.1
   ┌──────────────────────────┐
   │  后端 API（v20）          │
   └──────────┬───────────────┘
              ↓
        botv 核心 / 记忆 / 调度
```

**硬规则**：后端 API **不监听外网**；外网只能打到网关。

## 两种入口，别混

| 来源 | 走哪条路 | 为什么 |
|---|---|---|
| **公网**：手机、外网浏览器、以后的小程序 | **网关**（HTTPS/WSS + JWT + 限流） | 必须鉴权、必须加密 |
| **本机**：DSH / Qoder / WorkBuddy 插件、本机 Web | **直连 `127.0.0.1:7070` 内部 API** | 同一台机器，不需要再绕一层 |

```
外网手机 ──HTTPS──▶ 网关 ──gRPC──▶ 内部 API
本机插件 ──HTTP───▶ 内部 API（127.0.0.1，仅本机可达）
```

**网关不是「所有流量的中间人」，而是「公网的守门人」。**

## 网关要做的五件事

| 职责 | 具体 |
|---|---|
| **鉴权** | 登录（密码 → JWT，`sub=user_id` + `role`）、token 校验、刷新、失败锁定 |
| **限流** | **按 user** 每分钟 N 次；超过返回 429 |
| **路由** | `/api/chat` → `/internal/chat`，路径和参数做映射；`user_id` 从 token 注入，不信客户端 |
| **TLS** | 只接受 HTTPS / WSS（本地开发可开 http 开关） |
| **审计** | 谁（`user_id`）、什么时候、调了什么、耗时多少（落 `gateway_log`） |

## 多用户（v20 起，网关负责登录映射）

- **登录**：账号/密码 → JWT；`sub=user_id`、`role=owner|admin|user`；刷新 token 不换 `sub`。
- **注册**：先邀请制（owner 生成邀请码），不做公开注册。
- **身份绑定**：QQ / Web / 桌面 / 手机绑定到同一个 `user_id`；解绑/换绑走 owner 确认。
- **隔离**：客户端请求体里的 `user_id` 一律忽略；网关只信 token 里的 `sub`，再通过 gRPC metadata 传给后端。
- **配额**：按 user 限流/限额；owner 可调；不按 user 建连接池，池共享。
- **审计**：`gateway_log` 必须带 `user_id`；按 user 可查。

| 角色 | 能做什么 |
|---|---|
| `owner` | 全部；管理用户、邀请码、配额；可看审计 |
| `admin` | 管理普通用户/内容；不能改 owner |
| `user` | 只能读写自己的记忆/历史/日程/日记/书架 |

## 红线

| 红线 | 原因 |
|---|---|
| **后端永不直连公网** | 后端无鉴权，暴露即失守 |
| **鉴权失败 3 次锁 5 分钟** | 防爆破 |
| **JWT 24h 过期 + 可刷新** | 长期有效等于没有 |
| **`user_id` 只从 token 的 `sub` 来** | 客户端 body/query 里的 `user_id` 一律忽略 |
| **跨用户访问 403** | 谁也不能用 A 的 token 读 B 的数据 |
| 密码只存 hash（argon2id） | 明文不可接受 |
| 限流默认**开**，按 user 计 | 关了就等着被打 |
| 日志**不记密码和 token 全文** | 只记前 6 位 |

**不做什么**：

- 不代理 NapCat / 不实现 OneBot；QQ 的限流在 QQ channel adapter，不在这里。
- 不碰 QQ 协议、消息段、QQ 登录；那些是 NapCat 的事。
- 不做「按 user 建连接池」；池共享，只做配额。

## 序列化：网关内部说 protobuf，对外说 JSON

> 客户端只认 JSON（浏览器/Flutter 都方便）；网关和后端之间是 **gRPC + Protobuf**。
> 网关因此多了一个职责：**协议转换**。

```
客户端  ──JSON/REST──▶  网关  ──gRPC/protobuf──▶  后端
                          │
                          ├─ 反序列化 JSON
                          ├─ 转成 proto 消息
                          ├─ 调后端
                          └─ proto 结果 → JSON（含错误码映射）
```

### 网关要处理的四件事

| 事 | 说明 |
|---|---|
| **协议转换** | REST/JSON ↔ gRPC/protobuf（手写转换即可，不引 grpc-gateway） |
| **字段映射** | JSON 的 `snake_case` ↔ proto 字段名（保持一致就免映射） |
| **错误映射** | gRPC code → HTTP 状态码（见下表） |
| **流式** | 后端 `?` 不需要；**主动推送**用网关自己的 WebSocket（从后端拉长连接） |

**错误映射**：

| gRPC | HTTP | 场景 |
|---|---|---|
| `OK (0)` | 200 | 成功 |
| `INVALID_ARGUMENT (3)` | 400 | 参数缺/格式错 |
| `UNAUTHENTICATED (16)` | 401 | 无 token / 过期 |
| `PERMISSION_DENIED (7)` | 403 | 越权访问别的 user |
| `NOT_FOUND (5)` | 404 | 会话/任务不存在 |
| `RESOURCE_EXHAUSTED (8)` | 429 | 限流 |
| `UNAVAILABLE (14)` | 503 | 后端未启动 |

### 代码位置

| 文件 | 作用 |
|---|---|
| `server/gateway/convert.py`（新） | JSON ↔ proto 消息转换 |
| `server/gateway/client.py`（新） | gRPC 客户端（连 127.0.0.1:7070） |
| `proto/gen/python` | 生成的 stub，网关和后端共用 |

### 为什么不用 grpc-gateway（自动生成）

| 自动生成 | 手写 |
|---|---|
| 省事 | 多几十行 |
| 出错难调 | 一眼看懂 |
| 依赖 Go 工具链 | 纯 Python |

多用户下接口还会变，**手写转换更容易控**。

### 验收（v21.0 加一条）

```bash
# 客户端发 JSON，网关转 proto，后端回 proto，网关转回 JSON
curl -s -X POST localhost:7080/api/chat \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <access>' \
  -d '{"target_id":"822891053","text":"在吗"}'
# 期望：{"ok":true,"data":{"reply":"...","bubbles":["..."]}}
# user_id 由网关从 token 的 sub 注入，客户端不传
```

## v21.0 · C++ 工程与代理（3 天）

| 单元 | 内容 | 验收 |
|---|---|---|
| U1 | 网关进程（可选 nginx 或 FastAPI 中间层，见下） | 能起 |
| U2 | `/api/chat` → gRPC `Chat`（JSON↔proto 转换） | 转发成功 |
| U3 | 后端**只监听 127.0.0.1**，网关是唯一外部入口 | 直连后端失败 |
| U4 | 健康检查 `/api/health` | 返回 200 |

**实现语言：C++（已定）**

| 部分 | 选型 | 理由 |
|---|---|---|
| HTTP/WebSocket 服务 | **Drogon**（或 cpp-httplib 起步） | Drogon 自带 WS + 异步 + TLS |
| 与后端通信 | **grpc++**（官方 C++ 实现） | 和后端 .proto 直接共用 |
| 序列化 | **protobuf**（protoc --cpp_out） | v20 的 .proto |
| JWT | **jwt-cpp**（header-only） | 轻，无额外依赖 |
| 密码 hash | **libsodium**（argon2id） | bcrypt 也行，sodium 更现代 |
| 限流 | 自写滑动窗口（内存） | 单机够用 |
| TLS | **OpenSSL**（Drogon 内置支持） | 证书直接用 |
| 构建 | **CMake + vcpkg/Conan** | 依赖可复现 |
| 测试 | **GoogleTest** | C++ 标准选择 |

**为什么 C++ 合适**

| 点 | 说明 |
|---|---|
| 性能 | 网关是唯一入口，扛得住压测 |
| 单二进制 | 部署只需要一个 `nao-gateway` 文件 |
| 与 grpc++ 同源 | protobuf 生成 C++ 代码，直连后端 |
| 长期运行 | 无 GC 抖动 |

**代价（要知道）**

| 代价 | 缓解 |
|---|---|
| 编译链重（protobuf/grpc/openssl） | 用 vcpkg 锁版本；CI 缓存 |
| 出错排查比 Python 难 | 单元测试 + 结构化日志 |
| 开发慢 | 逻辑简单（鉴权/转发/限流），不写业务 |

## v21.1 · 鉴权（3 天）

| 单元 | 内容 | 验收 |
|---|---|---|

| 单元 | 内容 | 验收 |

## 新增表

```sql
CREATE TABLE gateway_log (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    ts         DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    client     VARCHAR(32) NULL,        -- web / app / cli
    method     VARCHAR(8) NOT NULL,
    path       VARCHAR(128) NOT NULL,
    status     SMALLINT NOT NULL,
    cost_ms    INT NOT NULL DEFAULT 0,
    ip         VARCHAR(64) NULL,
    KEY idx_gw_time (ts),
    KEY idx_gw_path (path, status)
);
```

## 验收（系列整体）

```bash
# 1. 没有 token 打不动
curl -s -o /dev/null -w '%{http_code}\n' localhost:7080/api/state     # 401

# 2. 登录后可用
TOKEN=$(curl -s -X POST localhost:7080/api/login \
        -d '{"user":"master","password":"..."}' | jq -r .data.access)
curl -s localhost:7080/api/state -H "Authorization: Bearer $TOKEN" | head

# 3. 直连后端打不动（只监听 127.0.0.1）
curl -s --max-time 2 192.168.0.56:7070/internal/state                # 连不上

# 4. 限流
for i in $(seq 1 80); do curl -s -o /dev/null -w '%{http_code} ' \
  localhost:7080/api/health -H "Authorization: Bearer $TOKEN"; done   # 出现 429
```

## 风险与处理

| 风险 | 处理 |
|---|---|
| 网关自己被绕过 | 后端**只绑定 127.0.0.1**（代码层保证，不靠防火墙） |
| token 泄露 | 24h 过期 + 可主动吊销（`!gw kick`） |
| 限流误伤自己 | 限流阈值可配，默认放宽 |
| 网关单点 | 只跑一个进程即可；挂了后端还在，重启就好 |
| **C++ 编译环境** | 用 vcpkg 锁版本；`build/` 不进版本库 |
| **内存安全** | 用 `std::string`/`span`，不用裸指针；ASan 跑一遍测试 |
| **崩溃排查** | 打开 core dump；日志带请求 id |
| 审计表涨太快 | 保留 90 天，按天写入 / 清理 |

## 与 v22（Web）/ v23（App）的关系

```
v21 网关  ← v22 Web、v23 App 都只连它
         ← 以后加 CLI / 小程序，也只改这里
```

**客户端永远不知道后端在哪**——这是网关存在的意义。
