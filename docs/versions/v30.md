# v30 系列 · 调度层插件接口

> 前置：v23 多用户 API / v28 存储层｜预估 3 天｜**三个次版本**
> 目标：把「事件怎么排队、几点触发、失败怎么重试」收进 **Scheduler + Trigger** 接口层。
> 默认仍是进程内 asyncio 调度器；以后换 DB 轮询/外部队列/多进程只换适配器。
>
> **核心不插件化**：进程内 asyncio 调度器是 native 实现，不注册为插件；
> 插件只能新增外部 trigger / 队列适配器；卸载/失败时回退进程内调度。
> 核心调度只能在启动前通过 `config/features.json` / `NAO_FEATURES` 关闭；插件不能运行时禁用。

## 现在的问题

| 现状 | 问题 |
|---|---|
| `scheduler/dispatcher.py` 写死进程内队列 | 换分布式/持久化要改业务 |
| `cron.py` 用 `loop.call_at` 挂钩子 | 重启丢失/时钟跳变无统一处理 |
| 重试/熔断在 worker 里 | 不能按触发源配 |
| 多用户任务混在一个队列 | 没法按 user 配额 |

## 契约

```python
class Scheduler(Protocol):
    def submit(self, kind: str, key: str, args=(), delay: float | None = None) -> bool: ...
    def cancel(self, key: str) -> bool: ...
    def stats(self) -> dict: ...

class Trigger(Protocol):
    def next_at(self, task: Task, now) -> datetime | None: ...
```

- `Scheduler`：投递/取消/统计；默认 asyncio 实现。
- `Trigger`：`once` / `interval` / `daily` / `weekly` / `cron`；只算下次时间。
- `SchedulerRegistry`：按配置选 scheduler；trigger 注册表。

## 关键设计

- **默认不引 Celery/Redis**：单进程 asyncio 队列够用；插件只是把接口留出来。
- **Trigger 只算时间**：不执行；执行仍走 Scheduler 的 worker。
- **重启**：cron 从 DB 重建 `next_ts`；错过不补发（沿用约定）。
- **时钟跳变**：看门狗定期对比 `next_ts`，过期且无 handle 就重排。
- **多用户**：key 带 `user_id`；每 user 有并发/队列配额。
- **可观测**：`!scheduler` 显示队列、worker、触发源、下次时间、失败/重试。

## 验收

```bash
!scheduler           # 队列 / worker / 下次触发 / 失败
```

- 换内存 scheduler：测试不依赖真实事件循环。
- 现有 `!cron once 下一分钟` 行为不变。
- A 用户塞满队列，B 用户仍能按时触发。

## 不做

- 不引入 Redis/Celery/消息队列。
- 不做分布式锁/多主调度（单进程）。
- 不做「错过补发」；仍按 v17 约定跳过。

## 风险

| 风险 | 处理 |
|---|---|
| 适配器改变定时语义 | 先包一层，保留旧路径开关；基线测试 |
| 重启丢钩子 | 从 DB 重建；看门狗 |
| 时钟跳变 | 定期对账；不依赖单次 `call_at` |
| 队列被单用户刷满 | 每 user 配额 + 有界队列 |
