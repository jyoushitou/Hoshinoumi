# v51 系列 · 语音通话

> 前置：v40（通道抽象）｜预估 6 天｜**先验证可行性，可能砍**
>
> 前面她能发语音、能转写你的语音，但那是「一条一条」的。
> 这一版尝试做**实时语音通话**：接通、对话、挂断。

## 第一步：确认可行性（1 天，可能直接砍掉）

QQ 没有公开的通话 API，NapCat 也不提供。可能的路径：

| 方案 | 做法 | 风险 |
|---|---|---|
| **A. 走 QQ 通话信令**（主选验证） | 逆向 NapCat 协议，看能否发起/接听 | 协议不稳定、掉线、封号 |
| B. 语音消息连续对话（退路） | 用现有语音消息 + 转写，模拟「一来一回」 | 有 3-5 秒延迟，不是真通话 |
| C. 不接 QQ，走本地麦克风 | 只在她和主人同机时可用 | 场景太窄 |

**第 1 天就是验证 A**：能不能发起一通、能不能收到对方的音频流。
拿不到就退到 B，v28 缩水为「语音连续对话」。

## 真做的话要解决四件事

| 问题 | 难点 |
|---|---|
| 音频流 | 双向实时音频（WebRTC / RTP） |
| 打断 | 她说话时你能插话（半双工变全双工） |
| 延迟 | 端到端 < 1.5 秒，否则像对讲机 |
| 成本 | 实时语音模型按分钟计费，比文字贵 10 倍以上 |

## 现成的轮子（GitHub 上找过）

| 项目 | 是什么 | 能不能用 |
|---|---|---|
| [qq-voice-call-bridge](https://github.com/mmmmm406/qq-voice-call-bridge) | QQ 语音通话桥接（Docker 部署） | **优先验证**：看它接的是哪套协议、要不要改 NapCat |
| [koishi-plugin-rtc-bridge](https://www.npmjs.com/package/koishi-plugin-rtc-bridge) | Koishi 的实时语音桥 | 参考实现，Node 生态 |
| [Lagrange.Core](https://github.com/LagrangeDev/Lagrange.Core) | 纯 C# 的 NTQQ 协议实现 | 看它的 Call 相关分支是否可用 |

**注意**：这些都是第三方逆向实现，协议随时可能失效。
所以第 1 天先跑通「能接通一次」，再谈集成。

## 通话记录要入库

> 通话是「发生过的事」，得留下痕迹——不然她永远不记得「昨晚聊了 12 分钟」。

表 `call_logs`（见 `docs/DB-DESIGN.md`）：

| 字段 | 说明 |
|---|---|
| `id` | 自增 |
| `target_id` | 和谁通话 |
| `kind` | `voice` / `video` |
| `direction` | `in`（他打来）/ `out`（她打去） |
| `started_at` / `ended_at` | 起止时间 |
| `duration_sec` | 时长 |
| `end_reason` | `hangup` / `timeout` / `error` |

**只记元数据，不存音频**——不录音、不落盘、不上传。

她可以在聊天里引用：「昨晚那通电话你说话含含糊糊的」——
靠的就是这张表，不是录音。

## 红线

- **只接主人的来电**，不主动拨打
- **通话记录要入库**（时长 / 起止 / 类型），**音频不落盘**
- 不录音、不上传第三方

## 退路（B 方案）

如果不能真通话，做「语音连续对话」：

```
你说一条语音 → 转写 → 回复 → TTS 语音条 → 你再说
```

延迟 3-5 秒，但体验接近对讲机，实现成本极低。

## 验收

| 项 | 标准 |
|---|---|
| 能接通 | 发起后 3 秒内听到她的声音 |
| 延迟 | < 1.5 秒（A）或可接受的对讲机延迟（B） |
| 挂断 | 任一方挂断后资源释放 |
