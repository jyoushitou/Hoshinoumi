# v17 系列 · 执行模型重构

> 前置：v16｜总计预估 40 天｜十三个次版本

## 现状：一个函数干所有事

`chat/handler.py` 的 `while True` 里混着：

```python
while True:
    rs = await ws.recv()              # 接入
    ...解析、去重、闸门...             # 业务
    async with get_target_lock(tid):  # 并发控制
        ans = await get_character_reply(...)   # 模型（同步阻塞！）
        await asyncio.sleep(...)              # 节奏
    await send_short_reply(...)       # 出站
```

同时 `schedule/runner.py` 里**另一个** `while True` 也在跑定时/主动/空闲。

### 六个具体病灶

| # | 病灶 | 后果 |
|---|---|---|
| 1 | 收消息和处理耦合在同一个循环 | 处理时读不到新消息（v17.3 连发合并做不了） |
| 2 | 同步 `requests`/浏览器/OCR 阻塞事件循环 | 抓小说时全系统卡住 |
| 3 | 两个独立主循环（handler + runner） | 定时和聊天互相不认识，无法统一调度 |
| 4 | 发送散落在 4 个文件，靠一把 `send_lock` 兜底 | 心跳/notice 能插进多气泡中间 |
| 5 | 没有统一观测 | 不知道谁在跑、跑多久、失败几次 |
| 6 | 所有能力平铺在 `botv/` 顶层 | 加功能只能继续往 handler 里塞 |

### 线程池 + 连接池（v17.0 核心基建）

两件事要一起上，否则会互相拖：

```
worker 协程 → run_blocking() → 线程池（3 线程）
                                  ↓ 每个线程
                              连接池借出 → 用 → 归还
```

| 池 | 作用 | 容量 |
|---|---|---|
| 线程池 | 把阻塞调用挪出事件循环 | `task_threads`=3 |
| 连接池 | 复用 MySQL 连接，避免每次建连 | `db_pool_size`=5 |

**关系**：连接池容量 ≥ 线程池容量（否则线程会等连接，等于串行）。

#### 连接池实现（不引入新依赖）

```python
class ConnPool:
    def __init__(self, size=5, timeout=5.0):
        self._q = queue.LifoQueue(maxsize=size)
        self._size = size
        for _ in range(size):
            self._q.put(self._new_conn())

    def acquire(self, timeout=5.0):
        conn = self._q.get(timeout=timeout)   # 等不到就抛，不无限阻塞
        if not conn.open:
            conn = self._new_conn()           # 断线重连
        else:
            try:
                conn.ping(reconnect=True)     # 顺手探活
            except Exception:
                conn = self._new_conn()
        return conn

    def release(self, conn):
        self._q.put(conn)
```

#### 三条纪律

| 纪律 | 原因 |
|---|---|
| **借了必还**（`try/finally`） | 漏还一次就少一条连接，跑久了池空 |
| **不跨长操作持有** | 调 AI 模型期间不该占着连接 |
| **事务在同一个连接内完成** | 池化后连接可能换，跨借出的事务会错 |

#### 连接池满了怎么办

| 情况 | 行为 |
|---|---|
| 5 秒内拿不到连接 | 抛错，任务失败并记日志（**不无限等**） |
| 连续失败 3 次 | 该任务 kind 熔断 1 小时 |
| 池里连接全断 | 逐个重建（`_new_conn`） |

#### 指标（进 `!stats`）

```
线程池：3/3 忙，队列等待 0
连接池：2/5 用，等待 12ms，重建 0 次
```

#### 随机主动也走事件（设计）

现在的主动消息是在 `runner.maybe_chat` 里 inline 判定的：`now.minute % 30 == 0` 才掷骰，判定和执行混在一起。改成**两级事件**：

```
proactive_tick（P1，每 30 分钟一次，自我重排）
      ↓ 六道闸门 + 掷骰
   命中 → 入队 proactive_say（P1，key=proactive:<tid>）
      ↓ worker 执行
   生成 → 出站 → 记账（proactive_count / unanswered）
```

| 事件 | key | 优先级 | 说明 |
|---|---|---|---|
| `proactive_tick` | `proactive:tick` | **P1** | 每 30 分钟自我重排，只做「判不判」 |
| `proactive_say` | `proactive:<tid>` | **P1** | 真正生成并发送；同人未完成时不重复入队 |

**为什么拆两级**：

| 好处 | 说明 |
|---|---|
| 判定和执行分离 | tick 很快（只读内存状态），不会占住 worker |
| 去重天然 | `proactive:<tid>` 在飞时，第二次 tick 不会重复生成 |
| 可观测 | `!stats` 能分别看到「tick 跑了几次」「说了几次」 |
| 和定时任务同构 | 都是「触发 → 事件」，不需要两套调度 |

**保留的约束**：主动仍是 P1（让路给 P0 聊天），深夜不说，连续没回应降频（v14-B2）。

**注意**：`proactive_say` 不走合并（v17.2 的合并只作用于**相邻定时消息**）——主动消息本来就是「突然一句」，合并会破坏语气。

## 改造策略：绞杀者模式

**不一次性重写，用新路径逐步替换旧路径。**

```
1. 新路径写好（并行存在）
2. 用开关切过去（NAO_NEW_PIPELINE=1）
3. 观察一周
4. 删除旧路径
```

| 阶段 | 新旧共存方式 |
|---|---|
| v17.0 | 只换「怎么调用」（阻塞→线程），行为不变 |
| v17.1 | 定时/主动/空闲走新调度；聊天仍走旧路径 |

**每一版都能单独上线、单独回滚。**

## 行为基线（最重要的一件事）

重构最大的风险是**悄悄改变行为**。所以 v17.0 第一件事是把现有行为固化成测试：

| 基线项 | 测什么 |
|---|---|
| 回复延迟 | 落在 1.5~3 秒（`delay_scale=1`） |
| 气泡数 | 模型给 N 行 → N 个气泡，上限 10 |
| 群聊闸门 | 3 秒间隔 / 6 条窗口 / @ 必回 75% |
| 记忆轮数 | 合并前 30 轮上限 |
| 命令 | 26+ 个命令仍可用 |
| 主动消息 | 六道闸门仍生效 |

**基线测试不全绿，不许开始改架构。**

## 风险

| 风险 | 处理 |
|---|---|
| 重构改崩 | 绞杀者模式 + 每版可回滚 + 基线测试 |
| 行为悄悄变化 | 基线测试 + 灰度开关 |
| 工作量超预期 | 4 版分批，每版独立可发布 |
| 新旧路径并存混乱 | 开关只留一个入口，旧路径标 DEPRECATED |
| 线程安全 | 线程本地连接；共享状态只在事件循环改 |

## 不做什么

| 不做 | 原因 |
|---|---|
| 换框架（不引入 FastAPI/Celery） | 现在的问题不是框架，是分层 |
| 重写业务逻辑 | 只搬位置，不改行为 |
| 数据库改表 | 与本次重构无关 |
| 引入消息中间件 | 单机场景，asyncio 队列够用 |

#### 前置建表（提前做）

**顺序固定为：装依赖 → 建表 → 自检 → 启动**

```
python3 scripts/setup.py             # 依赖 + 建表（默认只检查）
python3 scripts/setup.py --install   # 缺依赖就装，装完建表
python3 scripts/preflight.py         # 完整自检（13 项）
python3 run.py                       # 启动
```

**为什么把「装依赖」挪进建表脚本**：没有 `pymysql` 连 import 都过不去，
更别说建表。这两件事本来就该在同一个前置步骤里，之前放在 preflight 里是错位的。

| 文件 | 作用 |
|---|---|
| `scripts/setup.py` | **前置步骤**：Python 版本 → 依赖检查/安装 → 建表（幂等） |
| `botv/infra/schema.py` | **唯一表定义**（现状表 + DB-DESIGN 纯表），全部 `IF NOT EXISTS` |
| `scripts/init_db.py` | 只管建表（默认只看，`--apply` 才建），排障用 |
| `scripts/preflight.py` | 13 项完整自检（依赖 / 静态检查 / 能力 / 网络 / 表结构…） |

**为什么提前做**：v17.5 换表时，新表得先存在于所有环境（本机、服务器、未来新机），
靠文档提醒一定会漏。做成幂等脚本后，任何环境跑一次就齐。

**安全边界**：只建不存在的表，**永不 ALTER 已有表**（改结构仍走 `scripts/migrate_*.py`）。

### v17.6.0 · 定时消息：表与钩子（4 天）✅ 已完成

#### 存储：独立表 `cron_tasks`（表要纯）

**不复用 `events`**——那是「记忆与事件流」，定时任务是「配置」。两类数据混一张表，查询和迁移都会别扭。

```sql
CREATE TABLE IF NOT EXISTS cron_tasks (
    id           VARCHAR(32)  NOT NULL PRIMARY KEY,
    target_id    VARCHAR(64)  NOT NULL,              -- 谁的
    when_type    ENUM('daily','weekly','workday','once') NOT NULL,
    when_hh      TINYINT      NULL,                  -- 时（0-23）
    when_mm      TINYINT      NULL,                  -- 分（0-59）
    when_dow     TINYINT      NULL,                  -- 周几（0=周一 … 6=周日）
    when_date    DATE         NULL,                  -- once 用
    text         VARCHAR(120) NOT NULL,              -- 发什么
    enabled      TINYINT(1)   NOT NULL DEFAULT 1,
    only_workday TINYINT(1)   NOT NULL DEFAULT 0,
    hits         INT          NOT NULL DEFAULT 0,
    last_fire    DATETIME     NULL,
    created_by   VARCHAR(64)  NULL,
    created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    KEY idx_target (target_id),
    KEY idx_enabled (enabled),
    KEY idx_when (when_type, when_hh, when_mm)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

**为什么不是 JSON 一列**：时分/周几要参与查询（「今天 22:30 有谁的任务」），拆成列才能走索引。

#### 视图（可选，给统一列表用）

```sql
CREATE OR REPLACE VIEW v_cron_tasks AS
SELECT id, target_id,
       CASE when_type
         WHEN 'daily'   THEN CONCAT('每天 ', LPAD(when_hh,2,'0'), ':', LPAD(when_mm,2,'0'))
         WHEN 'weekly'  THEN CONCAT('每周', ELT(when_dow+1,'一','二','三','四','五','六','日'), ' ',
                                    LPAD(when_hh,2,'0'), ':', LPAD(when_mm,2,'0'))
         WHEN 'workday' THEN CONCAT('工作日 ', LPAD(when_hh,2,'0'), ':', LPAD(when_mm,2,'0'))
         ELSE CONCAT(DATE_FORMAT(when_date,'%m-%d'), ' ', LPAD(when_hh,2,'0'), ':', LPAD(when_mm,2,'0'))

```

#### 加载与触发

**每天 04:00 对账一次**（03:00 是写日记，避开放一起）：

| 时刻 | 做什么 |
|---|---|
| **新建任务时** | **立刻算下次触发 + 立刻建钩子**（不等 04:00） |
| 删除 / 暂停时 | 立刻取消钩子 |
| 启动时 | 全量对账一次（进程重启后钩子不在了） |
| **04:00** | 全量对账（跨天重排、清理失效、纠漂移） |
| 触发时 | 走钩子，不查库 |

**关键**：04:00 不是「注册入口」，只是**每天一次的校准**。
早上 8 点说「今晚 11 点提醒我睡觉」，钩子当场就建好，当晚 11 点就会响。

#### 钩子机制（call_at，不是每分钟扫）

```python
# 04:00 对账
for task in enabled_tasks:                 # 来自 DB
    next_ts = compute_next(task, now)
    handle = loop.call_at(next_ts, fire, task)
    hooks[task.id] = handle

for task_id in set(hooks) - set(enabled_ids):   # 被删/被停用
    hooks.pop(task_id).cancel()
```

| 规则 | 说明 |
|---|---|
| 建钩子 | 新任务 / 启用 / 改了时间 → 重算下次触发并重建 |
| 取消钩子 | 删除 / 暂停 → `handle.cancel()` |
| 触发后 | 自己重排下一次（`daily` → 明天同刻） |
| 进程重启 | 全量重建（钩子不持久化，DB 才是真相） |
| 兜底扫描 | 每分钟轻量检查「有没有已过期未触发的」，防时钟跳变 |

**为什么用 `call_at` 而不是每分钟扫表**：扫表要每秒/每分判 20 条 × N 人；钩子只在到点时醒一次，且**精确到秒**。兜底扫描只做「漏检查」，成本极低。

#### 时区

- DB 存 UTC（`DATETIME`）
- 计算下次触发时转 CST 再转回 UTC
- 触发判断用 `time.time()`，不受本地时区影响

#### 两种建立方式（都要有）

定时消息不能只靠「人改数据库」，两个入口：

| 入口 | 场景 | 例子 |
|---|---|---|
| **对话提取**（主） | 随口一说就建 | 「明天七点叫我」「每晚十一点提醒我睡觉」「周五提醒我交报告」 |
| **命令预设**（辅） | 精确控制 / 批量 | !cron add 07:00 daily 叫我起床、!cron list、!cron del 3 |

**对话提取的规则**：

`
消息进来 → 正则粗筛（时间词 + 提醒动词）
   ↓ 命中
解析：时间（明天/每天/周X/具体钟点）+ 事件（去掉时间词后的动宾）
   ↓
模糊就不建：时间说不清 → 只记日程（agenda），不建定时
   ↓ 清楚
先回一句确认：「七点叫你。要每天吗？」→ 主人回「每天」再升级为 daily
   ↓
入库 cron_tasks（source='chat'）+ 回复确认
`

| 规则 | 说明 |
|---|---|
| 只从**主人**的私聊提取 | 群里别人说「七点叫我」不该建 |
| 一次只建一条 | 一句话里多个时间 → 只取第一个，其余转日程 |
| 不猜日期 | 「下周」这种模糊说法不建，回问一句 |
| 可撤销 | 建完回一句「不要就说 !cron del <id>」 |
| 去重 | 同时间同事件 5 分钟内不重复建 |

**命令预设**：

`

!cron add 07:00 daily 叫我起床
!cron add mon,fri 20:00 提醒我健身
!cron once 2026-11-15 09:00 交报告

- 时间格式固定 HH:MM，星期用 mon,tue,...，一次性的用 once YYYY-MM-DD HH:MM
- 建完立即生效（不必等 04:00 对账）
- 命令建的 source='command'，对话建的 source='chat'，便于排查

#### 钩子：一个任务一个一次性定时器（不是轮询）

**先纠正一个错误做法**：用 loop.call_later 自我重排的 tick（现在的 minute_tick）
本质还是**循环扫描**——每 30 秒醒来问「有任务到点吗」，99% 的时间在空转。

正确的钩子是**每个任务一个一次性定时器**：

`python
# 新建任务
handle = loop.call_at(task.next_ts, _fire, task)

def _fire(task):
    sched.submit(cron_task, fcron:{task.id})     # 交给 worker，钩子只投递
    task.next_ts = compute_next(task)                 # 算下一次
    handles[task.id] = loop.call_at(task.next_ts, _fire, task)   # 重新上膛
`

| | 轮询 tick | 一次性钩子 |
|---|---|---|
| 定时器数量 | 1 个扫全部 | **N 个任务 = N 个** |
| 到点判断 | 每 30 秒比对分钟 | 定时器自己到点 |
| 空转 | 一直醒着 | **空闲零开销** |
| 精度 | 秒级（对齐 30 秒） | 毫秒级 |
| 代价 | 每个任务都要被扫到 | 只在到点醒一次 |

**「重新上膛」不算循环**：循环是「固定间隔去问」，钩子是「睡到那个时刻被叫醒，干完再睡」。

#### minute_tick 的拆分

现在的 minute_tick 是过渡产物（30 秒轮询），v17.4 拆掉：

| 职责 | 归宿 |
|---|---|
| 定时场景派发 | **per-task 钩子**（cron_tasks 每行一个 call_at） |
| 跨天初始化 | 钩子（0:00 挂一个） |
| 写日记 | 钩子（3:00） |
| 生日检查 | 钩子（每年 9/6 12:00、11/13 8:00） |
| 代码模式超时 | **保留轮询**——本身就是「检查是否超时」，没有明确时刻 |
| 日程/待办查询 | **保留轮询**——本身就是「查一遍列表」 |

**判断标准**：有明确时刻的 → 钩子；只是「隔一会儿查一下」的 → 保留轻量轮询。

#### 钩子的生命周期

| 事件 | 动作 |
|---|---|
| 新建任务 | 立刻 call_at 挂上（不等 04:00） |
| 修改时间 | cancel() 旧的 → call_at 新的 |
| 删除 / 暂停 | cancel() |
| 触发 | 投递事件 → 算下次 → **重新上膛** |
| 进程启动 | 从 DB 全量重建（钩子不持久化） |
| 04:00 | 全量对账：重建漂移的、清理失效的 |
| 进程退出 | 全部 cancel() |

**钩子本身不做任何业务**：只 submit。超时、重试、熔断全在 worker 里。

#### 线程模型（目标形态）

**一个主线程 + 一个监护线程，其余全是协程。**

| 谁 | 数量 | 干什么 |
|---|---|---|
| **主线程** | 1 | 跑事件循环（`app/loop.py` 的 `serve`） |
| **线程池** | **5** | `run_blocking` 的阻塞调用（模型 / 浏览器 / OCR / 下载） |
| **连接池** | **6** | MySQL 连接（比线程池多 1，留一条给监护/查询） |
| **监护线程** | **1** | 一个线程同时看两个池（不再各开一个） |

```
主线程 ── 事件循环 ── 调度器 / worker 协程 / WebSocket
   │
   ├── 线程池 5 条（阻塞调用）
   ├── 连接池 6 条（数据库）
   └── 监护线程 1 条（每 60 秒看两个池）
```

**监护线程做什么**（一个线程、两个池）：

| 检查 | 报警条件 |
|---|---|
| 线程池排队 | 排队 ≥ 3 → 记日志「线程不够或任务卡住」 |
| 连接池借出 | 空闲 0 且借出 = 容量 → 「疑似泄漏」 |
| 借连接超时 | 超时次数 ≥ 1 → 记日志 |

- 监护线程**不碰数据库、不做业务**，只读计数
- 自身异常必须吞掉（它是最后一道观测，不能自己挂）
- `!stats` 里显示一行：`🩺 监护：运行中（12 次） | 线程 5 排队 0 | 连接 4/6`

#### 死循环盘点（只保留主循环）

| 位置 | 现在 | 目标 |
|---|---|---|
| `app/loop.py` `serve` | `while True` | ✅ **保留**——这就是主循环 |
| `chat/handler.py` `ws.recv` | `while True` | ✅ 保留——连接驱动的阻塞等待，断开即退 |
| `heartbeat.py` `heartbeat_monitor` | `while True` + sleep | 🔻 改成调度器上的 `heartbeat` 事件（30 秒），不再自建循环 |
| `schedule/runner.py` `cycle_task_run` | `while True: sleep(3600)` | 🔻 **删除**——启动完就返回，保活归主循环 |
| `scheduler/workers.py` `_worker` | `while not stopped` | 🔻 改成「队列有活才起协程」，空闲时不留常驻 worker |
| `chat/coalesce.py` | `while True`（有界） | ✅ 保留——flush 后 return |
| `infra/pool.py` `close_all` | `while True`（有界） | ✅ 保留——队列空即 break |

**原则**：

> 只有**主循环**可以无限跑。其余循环必须有明确退出条件，
> 或者改成「事件驱动」（来活才醒），不留空转的常驻协程/线程。

#### 时间偏移（抖动）

「上下偏移」是**每次触发**的属性，不是任务的属性——每算一次下次触发就重新掷一次骰子，
所以每天的时间都不一样，不会固定。

| 任务类型 | 偏移 | 例子 |
|---|---|---|
| daily / weekly（习惯型） | **±10 分钟**（可配 jitter_min） | 07:30 → 今天 07:24、明天 07:37 |
| once（一次性） | **不偏移** | 「明天 9 点交报告」必须 9:00 |
| 阈值触发（如「十分钟后」） | 不偏移 | 说了几分钟就是几分钟 |

**两条规则避免「谁算谁覆盖」**：

1. **算下次触发 = 掷一次骰子**，结果写进 
ext_ts；不重复掷
2. 04:00 对账只重排「今天还没触发」的任务；已经触发过的看 last_fire，不回头改
3. 触发后自我重排时再掷一次（那是明天的）

换句话说：

`
04:00 对账 → 为今天剩余任务掷骰 → next_ts 写入
到点触发 → last_fire = 计划时间 → 为下次掷骰 → next_ts 写入
`

同一时刻只有一个 
ext_ts，不会出现「04:00 算一个、触发时又算一个」的打架。

#### 错过不补发

进程挂了、机器关机、卡顿太久导致的错过，**一律跳过，不补发**：

| 情况 | 处理 |
|---|---|
| 触发点已过去 > 60 秒 | 跳过，重算下一次 |
| 凌晨错过的「该睡了」 | **明天再说**，不早上补一句 |
| 只错过一次性的（`once`） | 标记 `enabled=0`，日志记一笔 |

**理由**：定时消息是「到点该说」的，晚了 5 小时补发只会显得诡异（早上收到「该睡了」）。宁可少说一句，也不说错。

对账时把 `last_fire` 更新为「计划时间」，这样兜底扫描不会反复捡起同一个过期点。

| U5 | 监护报警：排队 ≥3 / 连接借满 / 借连接超时 | `!stats` 能看到 |

**监护线程只读计数**：线程池排队、连接池空闲/借出/超时。不碰数据库、不做业务，
自身异常必须吞掉——它是观测，不能自己挂。

**死循环原则**：死循环允许存在，但**只能有一个，而且必须在主循环里**（`app/loop.py serve`）。
保活不是另开一个循环，而是主循环自己「等 shutdown 事件」——那本身就是保活。
worker、心跳要么有退出条件，要么改成「来活才醒」。

#### 看书的两处行为


**① 自发读书的门槛太高（2 小时 → 5 分钟）**

`botv/life/reading.py` 里现在是：

```python
IDLE_HOURS = float(os.getenv("NAO_READ_IDLE_HOURS", "2"))
def is_idle(last_user_ts, now=None):
    return (_now(now).timestamp() - last_user_ts) >= IDLE_HOURS * 3600
```

要连续 **2 小时**没聊天她才肯去读书——等于几乎不读。

改成 **5 分钟**，并且可配：

```python
IDLE_MINUTES = float(os.getenv("NAO_READ_IDLE_MINUTES", "5"))
return (_now(now).timestamp() - last_user_ts) >= IDLE_MINUTES * 60
```

**② 明确让她读书时，她说「不看」**

现象：跟她说「看看这本书」，她只把书加进追书列表，不立刻读；
日志里 `read_once` 直接返回「刚聊过」。

根因在 `read_once` 第一行：

```python
ok, why = should_read(None, now)   # 第一步就过「安静闸门」
if not ok:
    return {"ok": False, "reason": why}
```

`should_read` 有两条闸门：**深夜** + **主人闲着**。
「闲着」是给自发读书用的；**被人明确要求时，刚聊过是必然的**（因为正在聊这件事），
所以永远不满足。

**修法**：

| 入口 | 闸门 |
|---|---|
| `idle_tick` 自发读书 | 深夜 + **5 分钟没聊天** |
| 对话里明确要求 / `!read` 命令 | **只保留深夜**，跳过「闲着」 |

具体：`read_once(..., force=False)`，`force=True` 时只查 `is_night`；
`follow_request` 加完书后以 `force=True` 读一章。

**验收**：

- 安静 5 分钟后，她自己会去读一章（不用等 2 小时）
- 说「看看这本」→ 30 秒内真的读一章并给感想（深夜除外）

**③ 要求她读书，必须真的读正文**

现在的 `follow_request` 只做到「把书加进列表」，没读正文；

**硬要求**：

| 步骤 | 必须发生 | 失败时 |
|---|---|---|
| 取目录 | 拿到章节列表 | 回「这本目录取不到」 |
| **取正文** | 抓到正文，长度 ≥ 200 字 | 回「正文取不到（可能需要登录/被拦）」 |

| 落进度 | `last_no` 前进一章 | — |

- 只说「我去看」但没调用 `fetch_chapter`
- 正文为空/太短还当成功

**验收**：

- 说「看看这本」→ 日志里能看到取目录 + 取正文 + 正文长度

#### 语音与文字重复

**现象**（截图）：连续 3 条文字气泡 → 一条 1 秒语音 → 又冒出一条文字，
内容是第一句的改写版（「没有就是没吃。」→「没有，就是没吃。」）。

**两条可能的链路**（都要查日志确认）：

| 假设 | 证据怎么找 | 说明 |
|---|---|---|
| A. 错字撤回与语音并发 | 日志搜「撤回」「打错字撤回」 | try_typo_recall 在发完 1.5 秒后撤回首句并重发；语音已经念过旧句子，于是「语音 + 重发文字」同时出现 |
| B. 语音后补发残句 | 日志搜 [发送] / 已发送 条数 | send_short_reply 分条与语音各自触发，导致首句被发两次 |

**目前的代码顺序**（chat/handler.py）：

`
try_typo_recall(first_line)      # 撤回+重发（有延迟）
send_short_reply(reply_text)     # 文字
maybe_send_voice(first_line)     # 语音（念首句）
`

	ry_typo_recall 是**异步延迟执行**的，所以它会晚于文字和语音落地——
这就是「底部又出现一条文字」的合理解释。

**修法（按优先级）**：

1. **发语音时跳过错字撤回**：语音念出来的内容没法撤回，撤回文字只会造成「说的和写的不一致」
2. 或者：	ry_typo_recall 改成「发送前拦截」（在真正发出去之前改字），而不是发完再撤
3. 加测试：语音命中时，不触发撤回重发

**验收**：出现语音的那条回复，**文字只出现一次**，且不被撤回。
