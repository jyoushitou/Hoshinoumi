# v23 系列 · 多用户（账号、身份、隔离）

> 前置：v22（网关：核心/鉴权/安全）/ v19（架构/API/对话底座）｜预估 13 天｜**五个次版本**
>
> v23 才引入真正的多用户：`users` / `identities` / `roles`，所有业务表加 `user_id`，
> 两个用户互相看不到对方的记忆、历史、日程、日记、书架、对话。
> v20–v22 网关先做 owner-only；v23 再把 users/登录/JWT 角色/邀请码接到网关上。

## 多用户模型

| 概念 | 定义 |
|---|---|
| `user_id` | 账号/租户：一个人类用户 |
| `identity` | 绑定到 user 的渠道身份：QQ 号 / Web 账号 / 桌面设备 / 手机 |
| `target_id` | 会话：私聊 = `user_id`；群 = 群号；Web = `thread_id` |
| `role` | `owner` / `admin` / `user` |

**规则**：

- 每个请求必须带 `user_id`；没有“不传就是主人”的默认。
- v23 引入 users / 登录 / 身份；v22 网关先只信 owner token；v23.3 把网关升级为 JWT `sub=user_id` + role。
- 本机直连按 owner；API 只信 token/网关，不信 body 里的 `user_id`。
- QQ 私聊首次消息自动建 `user`（role=user），owner 可封禁；群聊归 owner/租户。
- 存量数据全部回填到 owner。
- **验收红线**：A 的 token/请求拿不到 B 的任何数据。

## v23.4 · 亲密度下降与修复（2 天）

> 现状：`relation.bump()` 只涨不降，摩擦状态（失望/冷战/怨念）不会影响亲密度。
> v23.4 增加确定性、可解释、可恢复的下降逻辑，不是随机扣分。

### 人的关系不是线性扣分

真实关系会**突然掉到 0，甚至变成负数**：

```text
平时 +0.005 累积
一次背叛/羞辱/越界 -> 信任崩塌 -> 直接归零或负数
不是“每次扣 0.03，扣 20 次才到 0”
```

所以亲密度范围改为：

```text
-1.0 ～ 1.0
```

档位增加负区间：

| 区间 | 档位 | 给模型的态度 |
|---|---|---|
| 0.70+ | 亲近 | 可以损、可以亲近 |
| 0.45–0.70 | 熟 | 正常开玩笑 |
| 0.20–0.45 | 认识 | 礼貌、有距离 |
| 0.00–0.20 | 陌生 | 客气、简短 |
| 0.00 | 归零 | 私聊回复概率最低 |
| -0.30–0.00 | 冷淡 | 减少主动、句短 |
| -0.60–-0.30 | 厌恶 | 拒绝亲近、带刺 |
| -1.00–-0.60 | 破裂 | 不主动、不交底、只保留基本功能 |

## 触发与幅度

| 事件 | 变化 | 说明 |
|---|---|---|
| 一次失望（期待超时） | -0.03 | 小摩擦，可累积 |
| 进入冷战 | -0.08 | 关系明显降温 |
| 怨念触发 | -0.15 | 长期未解决 |
| 连续 3 天无互动 | -0.01/天 | 冷落衰减，每周上限 -0.05 |
| 谎言被确认 | -0.20 | 信任受损 |
| 公开羞辱 / 持续越界 | -0.30 ～ -0.50 | 关系快速恶化 |
| 原则性伤害 / 背叛 | `aff = min(0, aff - 0.5)` | **可一次掉到 0 或负** |
| 彻底破裂事件 | `aff = max(-1.0, aff - 1.0)` | 可一次到负数 |
| 道歉 / 持续修复 | +0.02/天 | 只能慢慢修，不能瞬间满血 |

规则：

- 亲密度下限 `-1.0`，上限 `1.0`；允许负值。
- 小事件按表扣；严重事件可以**跳变**，不受每日上涨上限保护。
- 下降单独记账，不能靠聊天把负数直接刷回来。
- 负值区间内，普通聊天不增加亲密度；只有道歉/持续关心触发修复。
- 修复最多恢复本次损失的一部分（例如 50%），会留下“疤痕”，不保证回到原值。
- 所有变化写 `relation_events`：
  `user_id/target_id/delta/reason/severity/created_at`。
- 只影响当前 `user_id + target_id`，不跨用户。
- 只改数值/档位/语气，不删除记忆、不禁用功能。
- 扣分必须由确定性事件触发，不能由模型心情随机决定。

### 私聊回复概率

亲密度归零/为负时，私聊**普通消息**的回复概率调到最低：

| 关系 | 普通私聊回复概率 |
|---|---|
| 亲近 | 1.00 |
| 熟 | 0.90 |
| 认识 | 0.70 |
| 陌生 | 0.40 |
| 冷淡 | 0.10 |
| 厌恶 | 0.03 |
| 归零 / 破裂 | **0.01（最低，可配置）** |

规则：

- 只对“普通私聊消息”生效；群聊、命令、安全相关消息不走这个概率。
- 道歉 / 和好 / 明确求助不跳过；否则会把修复路堵死。
- `aff <= 0` 时统一用最低概率，不再按“陌生”处理。
- 随机跳过时记日志/指标，不调用模型，避免白花 token。
- 最低概率可配 `NAO_MIN_REPLY_PROB`（默认 0.01），但不建议设 0。
- 同一条消息只 roll 一次，不反复重试提高概率。

### 验收

```bash
!relation
# 关系：冷淡（-0.18）
# 最近变化：-1.00（11-13 信任崩塌）
# 修复中：道歉后 +0.02/天，最多恢复本次损失 50%
```

- 一次严重事件可以把 0.75 直接打到 0 或负数。
- 亲密度最低 -1.0，最高 1.0。
- 负值下普通聊天不涨；道歉/持续关心才慢慢修。
- 修复不会瞬间回到原值，会留疤。
- 扣分有 deterministic 原因和审计，不是随机惩罚。
- `aff <= 0` 后普通私聊回复概率最低；道歉、命令、安全消息仍会处理。
- 同一条普通私聊只 roll 一次，不靠重试硬刷回复。
- A 的摩擦不会改 B 的亲密度。

### 首次密码流程（QQ）

```text
用户第一次私聊
  -> 查/建 user_id=QQ
  -> password_hash 为空
  -> 提示“第一次见面，先设个密码（至少 8 位）”
  -> 下一条消息作为密码
  -> 存 hash
  -> 回复“密码设好了”
  -> 之后正常聊天/不使用命令
```

主人 QQ 跳过设密码；主人仍用 owner secret / 管理登录。

### 自有客户端首次登录

```text
owner 在 QQ 里发：
  !adduser 123456789

机器人回复：
  已创建客户端账号 123456789
  一次性 setup code: XXXX-XXXX
  24 小时内有效

客户端第一次连接：
  user_id=123456789
  setup_code=XXXX-XXXX
  新密码=用户自己输入

登录成功后：
  setup_code 立即作废
  之后只用 QQ + 密码登录
```

### 迁移与兼容

- 备份数据库和 `config.local.json`。
- 迁移：
  ```text
  users.id __owner__ -> MASTER_QQ
  identities.user_id
  invites.created_by / used_by
  gateway_log.owner
  所有业务表 user_id
  relation_events.user_id
  ```
- `target_id` 不改成 user_id；私聊 target 仍可用 QQ 号。
- 旧 `__owner__` 只作为迁移兼容，不再作为新数据 owner。
- 迁移失败可回滚到备份；不要只回滚代码不回滚数据。
