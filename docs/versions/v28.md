# v28 系列 · 多端推送（主动消息 fan-out）

> 前置：v23.3 多用户 API / v26 通道层｜预估 6 天｜**四个次版本**
> 位置在客户端（v30 Web / v31-32 桌面 / v33 手机 / v46 嵌入式）**之前**：
> 这一版先把 Endpoint 注册表 + DeliveryHub + 协议做出来，用**两个测试入口 + QQ**验收；
> 真实客户端在 v30+ 接入时只需注册，不改 hub。
> 目标：她的**主动消息**（定时、提醒、主动搭话、读书分享…）不是只发到某一个入口，
> 而是发到这个 `user_id` 绑定的**所有接入口**：QQ、Web、Linux/Windows 桌面、手机、嵌入式屏。
> 手机在忙、电脑关着，墙上的屏也能收到；反过来也一样。

## 现在为什么只有一个入口

| 现状 | 问题 |
|---|---|
| `send_short_reply(target, ..., ws)` 只带一个 `ws` | 一次只能发一个连接 |
| `cfg.active_ws_qq` 只有一个 QQ 连接 | QQ 侧单点 |
| Web/桌面/手机各自一条 WS | 没有「这个 user 有哪些入口」的注册表 |
| 主动消息直接调 `send_short_reply` | 谁在执行就发给谁，其他入口收不到 |

**结论**：缺一层 **Endpoint 注册表 + DeliveryHub**，主动消息先交给 hub，由 hub 扇出到该 user 的所有入口。

## 模型

| 概念 | 定义 |
|---|---|
| `endpoint` | 一个接入口：`endpoint_id` + `user_id` + `channel` + `device_id` + 连接 |
| `channel` | `qq` / `web` / `desktop-linux` / `desktop-win` / `mobile` / `embedded` |
| `message_id` | 一条主动消息的全局 id；所有入口收到同一个，客户端按它去重 |
| `DeliveryHub` | 注册入口、扇出、离线队列、重试、ack |

```
主动源（cron / proactive / reminder / idle / share / birthday）
        ↓
   DeliveryHub.push(user_id, message, kind="proactive")
        ↓ 查该 user 的所有 endpoint
   ┌────┼────────┬──────────┬──────────┐
  QQ   Web    Linux 桌面   Windows 桌面  手机 / 嵌入式屏
```

## 投递语义

| 项 | 规则 |
|---|---|
| 主动消息 | **扇出到该 user 的所有已绑定入口**，在线的立即发，离线进队列 |
| 聊天回复 | **只回来源入口**（谁问的回谁），不镜像到所有端，避免刷屏 |
| 去重 | 同一条 `message_id` 每个入口只投一次；客户端也按它去重 |
| 重试 | 至少一次；失败重试 3 次，仍失败进离线队列 |
| 离线补发 | 重连后按 `last_ack` 补发；默认保留 7 天 / 每端 200 条 |
| 顺序 | 同一入口按 `message_id` 递增；跨入口不保证同时到达 |
| 限额 | 每入口有界队列；满了丢最旧并计数，不拖垮 hub |
| 隔离 | 只查该 `user_id` 的 endpoint；绝不跨用户 |

## 关键设计

- **注册**：客户端连上 WS 时带 JWT（`sub=user_id`）+ `device_id` + `channel`，服务端登记；
  断开注销。同一 `device_id` 重连替换旧连接，不重复。
- **消息 id**：hub 生成 `message_id`（ULID/雪花），先落 `delivery` 表再扇出；崩溃后可恢复。
- **端点表**：`endpoints(user_id, endpoint_id, channel, device_id, last_seen, last_ack)`；
  `delivery(message_id, user_id, endpoint_id, payload, state, attempts, created_at)`。
- **扇出**：`asyncio.gather` 并发投递；单入口失败不影响其他入口。
- **QQ 入口**：NapCat 仍是一个 channel；hub 通过 QQ channel adapter 发，不直接碰 `ws.send`。
- **Web/桌面/手机/嵌入式**：都走各自 channel 的 WS/长连接；hub 不关心底层。
- **静音**：入口可以设「免打扰」，消息仍投递，只是客户端不弹通知；不因此少发其他入口。
- **聊天回复**：保留原路径，只回来源；如果来源是 Web，就回 Web，不发 QQ。
- **降级**：hub 挂了，主动消息进 `pending` 表，恢复后补发；不丢。

## 客户端接入排期

| 版本 | 入口 | 接入方式 |
|---|---|---|
| v28 | QQ + 2 个测试 WS 入口 | 本版验收 |
| v30 Web | `web` | 登录后注册 endpoint |
| v31 / v32 桌面 | `desktop-linux` / `desktop-win` | 同 Web |
| v33 手机 | `mobile` | 同 Web |
| v46 嵌入式屏 | `embedded` | 同 Web |

**v28 不依赖这些客户端**：测试入口用本地 WS 客户端模拟；真实客户端后续注册即可。

## 验收

```text
绑定：QQ + 两个测试 WS 入口（A/B）
触发：!cron once 下一分钟 提醒我喝水
期望：3 个入口在 10 秒内都出现同一条 message_id
```

| 项 | 标准 |
|---|---|
| 全入口 | 在线入口全部收到；离线入口重连后补到 |
| 去重 | 同一入口不重复；客户端按 `message_id` 去重 |
| 隔离 | A 的主动消息不会出现在 B 的任何入口 |
| 聊天 | 只在来源入口回，不镜像 |
| 观测 | `!endpoints` 列出每个入口的在线/积压/最后 ack |
| 稳定性 | 一个入口超时/断线，不影响其他入口 |
| 可扩展 | v30+ 新客户端只注册，不改 hub |

## 风险

| 风险 | 处理 |
|---|---|
| 同一条消息在手机+桌面同时弹，觉得吵 | 客户端按 `message_id` 去重；入口可设免打扰 |
| 离线队列无限涨 | TTL 7 天 + 每端 200 条 + 满了丢最旧并计数 |
| 扇出放大 QQ 调用 | QQ 只有一个入口；其他入口不走 QQ API |
| 重连风暴 | 指数退避；同 `device_id` 替换旧连接 |
| hub 崩溃丢消息 | 先落 `delivery` 表再投；启动恢复 pending |
| 跨用户泄露 | 只查 `user_id` 的 endpoint；单测覆盖 |

## 不做

- 不做跨用户广播。
- 不做聊天回复的全端镜像（只回来源；主动才 fan-out）。
- 不承诺 exactly-once；**at-least-once + 客户端按 `message_id` 去重**。
- 不在这一版接 APNs/FCM 专有推送；手机推送仍走 v33 的长连接/通知通道。
- 不为每个入口建连接池；入口只是连接，池仍共享。
