# v25 系列 · 内部通讯升级（8+4+body TCP + protobuf）

> 前置：v24 读书修复 / 本地阅读队列｜预估 8 天｜**五个次版本**
>
> 目标：**外部 → 网关仍走 HTTP/JSON**；**网关 → 后端走本机 TCP + protobuf**。
> 后端最终**只绑 3001 和 27004 两个端口**：
> - `3001`：NapCat WebSocket
> - `27004`：8+4+body 自定义帧 + protobuf
> 外部 `/api/*` 仍由网关 `27005` 提供 HTTP/JSON。
>
> 原 v25（插件接口）顺延为 v26；v25 及以后整体 +1。

## 为什么做

- 内部路径不需要人类可读 JSON
- protobuf 有字段号，加字段兼容
- TCP 长连接省掉每次 HTTP 建连/解析开销
- 帧边界明确，便于做超时/重连/限长
- 与 v23 proto 契约对齐


## 通讯边界（明确）

```text
外部客户端 / Web / App / DSH
        │
        │ HTTP/JSON + JWT
        ▼
   gateway 27005
        │
        │ 8+4+body TCP 帧 + protobuf
        ▼
   backend 27004
        ▲
        │ WebSocket（NapCat 协议）
   NapCat 3001
```

| 链路 | 协议 | 序列化 | 端口 |
|---|---|---|---|
| 外部 → 网关 | HTTP/1.1 | JSON | 27005 |
| 网关 → 后端 | 自定义 TCP 帧 | protobuf | 27004 |
| NapCat → 后端 | WebSocket | NapCat 消息 | 3001 |

规则：

- **后端不监听 HTTP**，27004 只接受 8+4+body 帧。
- **网关对外仍是 HTTP/JSON**，`/api/*` 契约不变。
- 网关负责鉴权、限流、审计，再把请求编码成 protobuf 帧。
- 后端只信任 127.0.0.1 上的网关帧；不做公网认证。
- 外部客户端不能直接连 27004。

### 一次 /api/chat 的路径

```text
客户端 POST :27005/api/chat  JSON
  -> 网关 JWT/限流/审计
  -> InternalRequest{request_id, method="/internal/chat", user_id, payload=ChatRequest}
  -> 8+4+body 帧 -> 后端 27004
  -> 后端 protobuf 解码 -> 业务
  -> InternalResponse{request_id, status, payload=ChatReply}
  -> 帧回传网关
  -> 网关转 HTTP JSON 响应
```

## 帧格式：8 + 4 + body

```text
偏移  长度  字段
0     4     magic = "NAO1"
4     1     version = 1
5     1     type: 1=request 2=response 3=event 4=ping
6     1     flags（保留，默认 0）
7     1     reserved（保留，默认 0）
8     4     body 长度，uint32 大端
12    N     protobuf body
```

规则：

- `8 + 4 = 12` 字节固定前缀，后面才是 protobuf。
- body 最大 8 MiB；超限直接断开并记录。
- 读帧必须处理**半包/粘包**：先读 12 字节，再按长度读 body。
- 长度不合法（0 或 >8MiB）→ 关闭连接。
- 连接是长连接；请求/响应靠 protobuf 里的 `request_id` 关联。
- TCP 只监听 `127.0.0.1:27004`，不暴露公网。
- 后端不绑定 27005；网关是独立进程/容器。

## Protobuf 封装

```proto
message InternalRequest {
  string request_id = 1;
  string method = 2;      // /internal/chat 等
  string user_id = 3;
  string role = 4;
  bytes payload = 5;      // ChatRequest / HistoryRequest ...
}

message InternalResponse {
  string request_id = 1;
  int32 status = 2;       // 200/400/401/403/404/429/503
  string error = 3;
  bytes payload = 4;
}
```

业务 payload 复用 `proto/nao/v1/nao.proto`，逐步补：

```text
ChatRequest / ChatReply
HistoryRequest / HistoryReply
StateRequest / StateReply
CronRequest / CronReply
DiaryRequest / DiaryReply
ShelfRequest / ShelfReply
AuditRequest / AuditReply
AuthVerifyRequest / AuthVerifyReply
```

## 端口/进程

```text
3001   NapCat WebSocket（后端绑定）
27004  内部 TCP + protobuf（后端绑定，只 127.0.0.1）
27005  HTTP 网关（独立进程/容器，不属于后端）

后端只有 3001 / 27004 两个监听端口。
```

## 迁移与回滚

- 27004 不能同时是 HTTP 和 TCP；v25 是**切换发布**，不是并存发布。
- 发布窗口：停 bot → 启 v25 后端（27004 TCP）→ 启 v25 网关 → 验收。
- 回滚：停 v25 → 启旧后端二进制（27004 HTTP）→ 启旧网关。
- 网关保留 `backend.protocol = "http" | "tcp"` 仅用于滚动回滚；最终默认 `tcp`。
- v25.4 删除网关内部的 HTTP 客户端路径与后端 aiohttp API。

## 验收

```text
1. 12 字节前缀正确，body 是 protobuf
2. 半包/粘包/超长/错 magic 都有测试
3. gateway -> 27004 完成 chat/history/state
4. 后端只监听 3001/27004，无 HTTP 监听
5. request_id 能正确配对并发响应
6. 后端断开返回 503；重连后恢复
7. 8MiB 限制生效
8. 切回 backend.protocol=http 可回滚
```

## 非目标

- 不做公网 TCP
- 不在 27004 上同时跑 HTTP 和自定义帧
- 不做自定义加密（本机回环；TLS 由外部入口负责）
- 不在最终版保留 27004 HTTP
- 不把外部 `/api/*` 改成 protobuf
