## 4. 数据结构：扩列，不建表

原来计划建四张表，改成**一次迁移**——`events` 扩成记忆主表，用 `kind` 区分内容。

```sql
ALTER TABLE events
  ADD COLUMN kind       VARCHAR(16)  NOT NULL DEFAULT 'event',
  ADD COLUMN dedupe_key CHAR(32)     NULL,
  ADD COLUMN importance TINYINT      NOT NULL DEFAULT 3,
  ADD COLUMN due_date   DATE         NULL,
  ADD COLUMN last_seen  DATETIME     NULL,
  ADD COLUMN hit_count  INT          NOT NULL DEFAULT 0,
  ADD COLUMN embedding  VARBINARY(2048) NULL,
  ADD INDEX idx_kind   (target_id, kind),
  ADD INDEX idx_dedupe (dedupe_key);
```

| kind | 用途 |
|---|---|
| `event` | 你的事（现有数据，`DEFAULT` 自动回填） |
| `fact` / `preference` | 关于你的事实与偏好 |
| `promise` | 承诺、日程（配合 `due_date`） |
| `life` | 她自己的生活事件（C17） |
| `profile` | 画像，一行 JSON |
| `summary` | 滚动摘要（B10） |

上限按 `kind` 分开保留，不再一刀切 20 条。

### 4.1 迁移（一次性）

1. `ALTER TABLE` 加列
2. 遍历现有行：归一化文本（去空白/标点、截断 80 字）→ `dedupe_key = md5(kind + 归一化文本)`
3. 同 `(target_id, kind, dedupe_key)` 合并：保留最早一条，删除其余，`hit_count` 累加，`last_seen` 取最新
4. 上限改成按 `kind` 分别保留（life 60 / user 30 / 其他 20）

### 4.2 三层去重

| 层 | 时机 | 规则 |
|---|---|---|
| 写入 | 每条入库前 | `dedupe_key` 命中且 7 天内 → 只更新 `last_seen` 与 `hit_count` |
| 生成 | 写 life 事件前 | 把最近 7 天的 life 事件喂给模型，明确「不许重复」 |
| 检索 | B11 之后 | embedding 余弦 > 0.9 视为同一条，合并 |

## 5. 数值与向量：用在哪、不用在哪

### 5.1 用：状态向量 + 惯性衰减

```
s = [mood, energy, loneliness, affinity]  ∈ [0,100]^4

每小时：s ← s + k·(base - s) + Δevent        k ≈ 0.05
```

- **有惯性**：不会因为你一句话就 180 度转弯，像人的情绪
- **有独立来源**：「小咪生病」「学生会挨批」也会改数值，不全由你决定
- **不可见**：只影响回复长度、语气、主动频率、延迟

| 条件 | 表现 |
|---|---|
| `mood < 30` | 短句、少表情、可能拒绝 |
| `loneliness > 70` | 主动找你 |
| `energy < 20` | 深夜回得慢、说困 |
| `affinity` 四档 | 称呼与语气渐变 |

### 5.2 用：检索矩阵

```
M ∈ R^{n×d}            # 每条记忆一行 embedding
scores = M · q         # 一次矩阵乘法算完所有相似度
top5 = argsort(scores)
```

embedding 用本地 `bge-small-zh`（512 维，CPU 毫秒级，不花钱、不出网）。

### 5.3 不用：把记忆压成矩阵

- 10000 条 × 512 维 × 4 字节 ≈ **20MB**，存储根本不是瓶颈，压它没意义
- PCA / 降维省的是几 MB，丢的是召回率
- 人记得的是「他周三说要答辩」这句话，不是一个向量
- **不压，靠检索**：原文全留，需要「近况」时用时间线（B16），不生成摘要
- 也**不建摘要表**：B10 已取消，少一个会漂移的中间层

## 6. 明确不做

- 不做状态条 / 数值面板
- 不做「亲密度充值」「每日签到」这类讨好型机制
- 不做惩罚式冷落（不回消息就被骂/被删）
- 不做自主长链思考（成本爆炸，人设也会变味）
- 不让她改自己的 prompt（人设必须是人写的）
