## 一、项目定位

### Q1：这个项目到底是什么？

A：一个以主人 QQ 为核心、允许受限用户接入的 QQ 角色陪伴系统。她不是客服，也不是通用 Agent，重点是：

- 有固定人设和生活状态
- 记得住对话、事实和关系变化
- 会按时间/事件主动说话
- 有独立的网关和后端边界

技术上是 Python 后端 + NapCat QQ 通道 + C++ 网关。v23.5 起支持 owner + 普通用户隔离。

### Q2：和普通 QQ 机器人有什么区别？

A：普通机器人多是“收到消息 → 调模型 → 回复”。这个项目多了：

- 长期记忆和事实卡
- 心情/精力/孤独等生活状态
- 关系里程碑、摩擦、冷战、和好
- 定时/日程/待办/主动消息
- 出站队列、重试、断线补发
- JWT 网关、限流、审计

### Q3：为什么要做这个？

A：想验证“长期陪伴”这件事能不能落到工程上：记忆怎么不忘、主动说话怎么不烦、模型失败怎么不崩、单机怎么跑得稳。

### Q4：它最核心的设计理念是什么？

A：**人设优先，记忆其次，事实再次**。不追求 100% 正确的知识库，追求“像她、记得你、行为连贯”。

## 二、技术架构

### Q5：整体架构是什么？

A：

```text
QQ / NapCat WebSocket
  -> 入站解析/去重
  -> 批处理/锁
  -> 命令或对话
  -> 记忆/生活/人设
  -> 模型 API
  -> 出站队列
  -> QQ

外部客户端 -> C++ 网关 27005 -> 后端 27004
```

### Q6：为什么后端用 Python？

A：模型调用、记忆检索、调度、文本处理都在 Python 生态里；开发速度快。性能瓶颈主要在模型 API 和 IO，不在 Python 计算。

### Q7：为什么还要一个 C++ 网关？

A：不是为了“显得高级”，是为了把公网入口独立出来：

- JWT 登录/刷新
- 统一 401/403/429/503
- 限流和审计
- 后端只监听本机
- Docker 交付，部署机不编译

网关用用户自己的 CommonNet（Boost.Asio/Beast）。

### Q8：为什么不用 FastAPI / Go / Node？

A：当前 aiohttp 足够；换栈不会自动解决记忆和调度问题。C++ 网关是因为已有 CommonNet，且需要独立鉴权边界。

### Q9：为什么同时支持 MySQL 和 SQLite？

A：MySQL 适合长期运行和多连接；SQLite 适合单机/测试/小部署。上层仓储不直接依赖具体数据库。

### Q10：消息处理是并发的吗？

A：同一个目标串行（锁），不同目标可以并行；阻塞调用放线程池；出站有队列和重试。

### Q11：定时任务怎么做的？

A：不是每分钟扫全表。用 `loop.call_at` 挂钩子，任务到点投递到调度器；有 generation 防止旧回调重复执行；看门狗只补缺失钩子。

### Q12：网关限流怎么做的？

A：进程内令牌桶，每 IP 60 次/分钟，超限 429，带 `Retry-After`。v22 先做单机；多实例要换 Redis/集中限流。

### Q13：审计会记录聊天内容吗？

A：不记录。`gateway_log` 只存 owner、path、status、耗时、IP、request_id；不存 token、secret、body。

### Q14：TLS 在哪里做？

A：v22 用独立的 TLS 终止代理（`gateway/tls_proxy.py`），网关本体仍是本机 HTTP。公网只暴露 TLS 端口，27005 不直接暴露。

## 三、记忆与模型

### Q15：她怎么“记得住”？

A：三层：

- 最近对话：短期窗口
- 长期记忆：BM25 + 关键词双路 RRF
- 事实卡/关系/生活状态：结构化存储

不是把所有聊天记录无脑塞进 prompt。

### Q16：上下文不会爆吗？

A：会做截断和检索；只取相关记忆、最近对话、事实卡，不把整个数据库塞进去。

### Q17：记忆会错吗？

A：会。所以她不是“永远正确”的知识库；重要事实走事实卡，普通记忆允许模糊。错记可以删/改。

### Q18：用的什么模型？

A：DeepSeek 和豆包双模型兜底；具体模型名和 Key 不公开。失败时返回兜底文案，不把错误当她的回复入库。

### Q19：模型挂了怎么办？

A：双模型切换；都失败时走兜底；网关后端断开返回 503；不阻塞 QQ 主循环。

### Q20：成本大概多少？

A：取决于 token 用量和模型价格，不给固定数字。可以现场说“按实际 API 账单”，不要编“每月几块钱”。

### Q21：延迟为什么有时很长？

A：模型 API 本身有延迟；项目还会做分条、延迟发送、拟人节奏。长延迟不等于卡死，但要有超时和降级。

### Q22：为什么不做微调？

A：当前用 prompt + 记忆 + 人设就能验证产品；微调成本和迭代速度不划算，也不是当前瓶颈。

## 四、生活、主动消息与边界

### Q23：她为什么会主动找我？

A：定时/事件触发后，先查状态和记忆，再决定说不说；有频率限制、免打扰时段和“上次没回应就降低频率”。

### Q24：会不会很烦？

A：会专门控制：概率、冷却、夜间静默、连续未回应降频。目标是“偶尔想起你”，不是推送机器。

### Q25：她的心情/关系是真的吗？

A：是状态机，不是意识。心情、精力、孤独、亲密度会随时间/互动变化，用来影响语气和是否主动，不是科学意义上的情感。

### Q26：亲密度会掉到负的吗？

A：已经实现：亲密度范围 -1.0～1.0，允许一次严重事件跳到 0 或负数；负值下普通聊天不涨，道歉/持续关心才慢慢修复；归零/负值普通私聊最低回复概率。

### Q27：她能替代真人吗？

A：不能，也不应该这样宣传。她是陪伴型角色，不是心理治疗、医疗建议或真人替代。

## 五、多用户与账号（v23.5）

### Q49：主用户是谁？

A：`MASTER_QQ` 指定的主人 QQ。它对应：

```text
user_id = MASTER_QQ
role = owner
```

只有 owner 能用 `!` 命令。其他用户 role=user，只能聊天/使用，不能执行命令。

### Q50：普通用户的 user_id 是什么？

A：直接是 QQ 号：

```text
user_id = QQ 号
```

不是随机 UUID，也不是再分配一个“内部账号”。QQ 身份通过 `identities` 表绑定：

```text
channel=qq, external_id=QQ -> users.id
```

### Q51：普通用户第一次私聊会发生什么？

A：

```text
第一次私聊
  -> 查 identity
  -> 没有就建 user_id=QQ、role=user、password_hash=NULL
  -> 提示“第一次见面，先设个密码（至少 8 位）”
  -> 下一条消息作为密码
  -> 存 PBKDF2 hash
  -> 回复“密码设好了”
  -> 之后才正常聊天
```

设密码前不调用模型，避免陌生人第一条消息就消耗 token。

### Q52：密码怎么存？

A：不存明文，存 PBKDF2-HMAC-SHA256：

```text
算法：PBKDF2-HMAC-SHA256
迭代：120000
盐：随机 16 字节
格式：pbkdf2$120000$salt$hash
```

数据库泄露时不能直接还原密码。

### Q53：设过密码之后怎么登录？

A：两种入口：

```text
QQ 私聊：QQ 身份已经由 NapCat 证明，不再每条消息问密码
Web/API：user_id=QQ + password
```

Web/API 首次登录如果没有密码，返回 `password_setup_required`，不签 JWT。

### Q54：自有客户端第一次连接怎么登录？

A：owner 先在 QQ 里发创建命令：

```text
!adduser 123456789
```

返回：

```text
已创建客户端账号 123456789
一次性 setup code：XXXX-XXXX
24 小时内有效
```

客户端第一次连接：

```json
{
  "user_id": "123456789",
  "setup_code": "XXXX-XXXX",
  "password": "用户自己输入的新密码"
}
```

首次成功后 setup code 立即作废，之后只验证 QQ + 密码。

### Q55：setup code 安全吗？

A：

- 只在创建时返回一次
- 数据库只存 hash
- 默认 24 小时过期
- 首次登录后立即清空
- 不能复用
- 不在日志/审计里记录

风险：owner 把 code 发错人；需要撤回/重新生成。

### Q56：owner 原来的 `__owner__` 数据怎么办？

A：v23.5 做了迁移：

```text
__owner__ -> MASTER_QQ
```

涉及：

```text
users.id
identities.user_id
invites.created_by / used_by
所有业务表 user_id
relation_events.user_id
gateway_log.owner
```

迁移前必须备份数据库；这不是纯代码升级。

### Q57：多用户是“一人一张表”吗？

A：不是。是共享表 + `user_id`：

```text
users
identities
roles
invites
memories(user_id, target_id, ...)
conversation_messages(user_id, ...)
cron_tasks(user_id, ...)
diaries(user_id, ...)
reading_progress(user_id, ...)
relations(user_id, ...)
relation_events(user_id, ...)
```

同一个数据库、同一个 MySQL 账号。不是每用户一个库，也不是全库一张表。

### Q58：怎么保证 A 看不到 B？

A：三层：

1. token 里的 `sub=user_id`
2. API 只信 token，不信 body 里的 user_id
3. 仓储/上下文强制 `user_id` 过滤

测试覆盖：

```text
A/B 记忆
A/B 历史
A/B 日程
A/B 日记
A/B 书架
```

### Q59：普通用户发命令会怎样？

A：不执行，明确回复：

```text
这个命令只有主人能用。
```

不会静默当成普通聊天，也不会给普通用户 owner 权限。

### Q60：群聊怎么算 user_id？

A：群聊归属 owner/租户，群友不是账号；群消息用 `speaker_id` 区分发言人。私聊才按 QQ 号建用户。

### Q61：封禁用户怎么处理？

A：`users.status`：

```text
active  -> 正常
banned  -> QQ 入站拒绝；API 登录返回 banned，不签 JWT
```

owner 可以改角色/状态；普通用户不能改别人。

### Q62：多用户限流是按用户还是 IP？

A：v22 当前是每 IP 60/min，进程内令牌桶。v23.5 还没做“按 user_id 的分布式限流”；多实例部署需要 Redis/集中限流。这是边界，不是已经完成的能力。

## 六、安全、隐私与合规

### Q28：聊天数据存在哪？

A：自己的数据库（MySQL/SQLite），不传到第三方数据库；但调用模型 API 时，相关内容会发给模型服务商。这个要如实说明。

### Q29：API Key 安全吗？

A：Key 在后端配置/环境变量里，不写前端、不进日志、不进 git。演示时绝不投屏 Key。

### Q30：公网怎么防？

A：JWT、限流、审计、后端只监听本机、TLS 终止、网关独立；v23.5 起 owner/普通用户隔离，普通用户没有命令权限。

### Q31：多用户为什么不是“再建一个数据库/账号”？

A：不是。还是同一个库、同一个 MySQL 账号，只是多张共享表 + user_id：users、identities、roles、invites，以及各业务表的 user_id。不是每个用户一套表，也不是全库一张表。

### Q32：NapCat 合规吗？

A：NapCat 是非官方 QQ 协议实现，存在账号风险和条款风险。项目按个人自托管、低频使用设计，不做商业群发/骚扰。

### Q33：角色版权呢？

A：这是个人同人/学习项目，不使用官方素材盈利；公开演示时注意角色版权和平台规则。

### Q34：能开源吗？

A：当前是个人项目，是否开源要看清理配置、密钥、隐私数据和第三方依赖许可；不建议直接公开整个运行环境。

## 七、工程与测试

### Q35：怎么保证不崩？

A：没有“保证不崩”。有看门狗、重试、出站队列、降级、备份；但不是高可用系统。

### Q36：测试多少？

A：当前 1017 条测试全绿（功能 + 环境/迁移），另有架构闸门检查长函数、events 读路径、启动 DDL、持久层环。

### Q37：架构闸门是什么？

A：`scripts/arch_check.py`：

- 不允许 >100 行函数
- 不允许运行代码读 `events`
- 启动不允许 DDL
- 不允许 log/settings 反向依赖数据库

不是形式主义，是防止架构重新腐化。

### Q38：部署复杂吗？

A：后端可以裸机跑；网关是 Docker 镜像；部署机不编译 C++。数据库迁移只有一个入口 `scripts/migrate.py --apply`。

### Q39：升级会丢数据吗？

A：迁移是增量的；升级前备份。回滚网关镜像容易，回滚数据库要看迁移是否有破坏性变更。

### Q40：为什么有这么多版本文档？

A：因为项目迭代久了，靠记忆会乱。每个大版本有目标、子版本、验收和边界，避免“加功能加散”。

## 八、演示与翻车预案

### Q41：现场 QQ 掉线怎么办？

A：提前录 2–3 分钟备用视频；现场先重启 bot，确认 `!status`；掉线就切视频，不现场 debug。

### Q42：模型超时怎么办？

A：说明有双模型/兜底；不要反复重试刷屏。演示问题优先用录屏。

### Q43：有人现场发奇怪内容怎么办？

A：用测试群/测试账号，不发生产入口；owner 命令不给观众；必要时关群聊或只投屏。

### Q44：token/密码被投屏了怎么办？

A：立即停止演示，换 secret，重启网关，旧 token 全部失效；不要把截图发群里。

## 十、路线与“下一步”

### Q45：接下来做什么？

A：按当前计划：

- v22：限流/审计/TLS/`!gw` 已完成
- v23/v23.5：多用户、角色、邀请码、QQ 首次密码、客户端 setup code、亲密度修复
- v24–v31：各层接口实现
- v32：默认链路选择
- v34–v36：本机服务化、DSH 插件、Qoder/WorkBuddy
- v37+：Web/桌面/手机；v40 手机端含记账
- v41：手机离线对话/记账同步

### Q46：最终形态是什么？

A：一个可自托管的、记得住、有生活、多端可用、对第三方可扩展的角色系统。不是公共 SaaS，也不是通用 Agent 平台。

### Q47：最想让大家记住什么？

A：不是“接了个模型”，而是：

```text
把长期记忆、生活状态、主动消息、出站可靠性、网关安全
这些脏活，真的落到了可运行的工程里。
```

### Q48：这个项目最大的坑是什么？

A：不是模型，是边界：

- 日志反向依赖数据库
- 启动时偷偷建表
- 定时钩子重复执行
- 网关没有统一鉴权
- 出站没有队列/重试

这些“不酷”的地方，才决定它能不能长期跑。

## 十一、不能回答 / 不该展示

- 真实 QQ 号、群号、聊天记录
- `NAO_GATEWAY_OWNER_SECRET`
- access / refresh token
- API Key、数据库密码
- 公网 IP、SSH 配置、证书私钥
- 服务器后台、Docker 环境变量截图
- 未公开的用户数据

被问到具体密钥/地址时，统一回答：

> 这些属于部署私密信息，不方便展示；可以讲架构和验证方式。
