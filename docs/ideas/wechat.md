# 接入微信（搁置）

> **状态：暂不实施。** 2026-11-10 决定不做微信接入，本文仅存档备查。
> 若以后要做，可从这里恢复成版本计划。

> 前置：v17（调度器 + 出站层）｜预估 12 天｜**四个次版本**

## 目标

除了 QQ，她也能在微信里说话——**同一个人格、同一份记忆**，只是换了个入口。

```
QQ 里：你：今天好累
微信里：你：今天好累
她：……（她记得 QQ 里说过的那句「加班到十点」）
```

## 三种微信通道（选哪种很重要）

| 通道 | 能力 | 限制 | 结论 |
|---|---|---|---|
| **企业微信（自建应用）** | 主动推送 + 接收消息 + 群机器人 | 需要企业主体（个人可注册小规模） | ✅ **优先** |
| **微信公众号** | 被动回复 + 客服消息 | **48 小时窗口**、被动回复 5 秒超时 | ✅ 次选 |
| **个人微信（hook/协议）** | 全功能 | **违反微信服务条款，封号风险极高** | ❌ **不做** |

**红线：不碰个人微信 hook。**理由：

- 协议逆向随时失效
- 账号一旦被封，连带绑定的支付/社交全废
- 属于明确违反 ToS 的用法

# v19.0.0 · 通道抽象层

## 为什么先做抽象

现在所有消息处理都假设「入口是 QQ」：

```python
ws.send(json.dumps({"action": "send_private_msg", ...}))   # 写死在 send.py
```

微信的消息结构、发送方式、限速全不一样。**先抽出接口，再接第二个通道**，否则会到处 if-else。

## 接口

```python
class Channel(Protocol):
    name: str                                    # "qq" / "wecom" / "mp"

    async def send(self, target: str, msg: Message) -> str:
        """发一条消息，返回平台消息 id"""

    def supports(self, feature: str) -> bool:
        """是否支持某能力：at / image / voice / poke / recall"""
```

`Message` 统一结构：

```python
@dataclass
class Message:
    text: str = ""
    images: list = field(default_factory=list)
    voice: bytes | None = None
    at: str | None = None        # 要 @ 谁
```

## 迁移策略

| 步 | 内容 |
|---|---|
| 1 | 新建 `channels/base.py`（接口 + Message） |
| 2 | 新建 `channels/qq.py`，把现有 `send.py` 包一层 |
| 3 | `egress/outbound.py` 改成「按 target 选通道」 |
| 4 | 现有 QQ 行为不变（基线测试兜底） |

**关键**：QQ 通道迁移完，基线 17 条必须还全绿——否则说明抽象层改变了行为。

# v19.1.0 · 企业微信适配器

## 能力

| 能力 | 企业微信 | 说明 |
|---|---|---|
| 发文本 | ✅ | 应用消息 |
| 发图片 | ✅ | 先上传素材 |
| 主动推送 | ✅ | 无 48 小时限制 |
| 接收消息 | ✅ | 回调 URL 校验 + 解密 |
| @ 人 | ❌ | 私聊场景不需要 |
| 语音 | ⚠️ | 可发语音文件，不可合成 |
| 撤回 | ⚠️ | 企业微信接口有限 |

## 关键实现

| 项 | 做法 |
|---|---|
| 认证 | `corpid` + `corpsecret` → `access_token`（缓存 2 小时） |
| 回调校验 | `msg_signature` + `AES` 解密（官方 SDK 逻辑） |
| 被动回复 | 5 秒内必须响应，否则回空串 |
| 主动消息 | 走 `message/send`，频率限制 20 条/分钟 |
| 用户标识 | `userid`（企业内唯一） |

## 限制与降级

| 情况 | 处理 |
|---|---|
| 48 小时内没互动 | 公众号不能主动发；企业微信可以 |
| token 过期 | 自动刷新并重试一次 |
| 频率超限 | 排队，按 20 条/分钟节流 |

# v19.2.0 · 公众号适配器

## 与企微的差别

| | 企业微信 | 公众号 |
|---|---|---|
| 主动消息 | 随时 | **只有 48 小时客服窗口** |
| 被动回复 | 5 秒 | **5 秒**（超时回「正在输入」不可行） |
| 用户标识 | userid | openid |
| 富媒体 | 支持 | 支持（素材接口） |

**48 小时窗口是硬约束**：用户 48 小时没说话，就不能主动推。这直接影响「主动消息」逻辑——在公众号通道下，主动消息只能落在窗口内。

## 处理

| 场景 | 做法 |
|---|---|
| 窗口内 | 正常主动消息 |
| 窗口外 | 排队，等用户下次说话再发（或丢弃并记日志） |
| 被动回复超 5 秒 | 先回「（正在想…）」，结果异步补发客服消息 |

# v19.3.0 · 身份统一

## 问题

QQ 和微信是两套 ID：

```
QQ: 822891053        → 记忆 target_id = "822891053"
微信: oX7abc...      → 记忆 target_id = "oX7abc..."
```

不统一的话，同一个人在两边的记忆、亲密度、日程全是分开的。

## 方案：绑定码

```
你（QQ）：!bind
她：绑定码：A7K2（10 分钟内有效）

你（微信）：绑定 A7K2
她：绑定成功，以后两边记忆是同一份
```

| 项 | 说明 |
|---|---|
| 绑定码 | 6 位，10 分钟有效，一次性 |
| 存储 | `events(kind='binding')`：主 ID ↔ 副 ID |
| 合并策略 | **记忆保留在主 ID**，副 ID 的 target 映射到主 ID |
| 解绑 | `!unbind` |

## 数据映射

```python
def resolve_identity(channel: str, uid: str) -> str:
    """任何通道的 uid → 统一的主 ID"""
    main = bindings.get(f"{channel}:{uid}")
    return main or f"{channel}:{uid}"
```

**没绑定的人**：用自己的通道 ID 单独存（互不干扰）。
**绑定后**：读写都落到主 ID。

## 风险

| 风险 | 处理 |
|---|---|
| 公众号 5 秒超时 | 先回占位，再异步补发 |
| 48 小时窗口 | 主动消息前先检查窗口 |
| 企微频率限制 | 20 条/分钟节流 |
| 身份绑定被冒用 | 绑定码 10 分钟 + 一次性 + 需主人确认 |
| 通道差异导致行为不一致 | 能力探测 `supports()`，不支持的功能降级而不是报错 |
| **个人微信诱惑** | 明确不做，写进红线 |
